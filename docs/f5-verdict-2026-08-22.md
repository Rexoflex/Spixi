## 1. ★ F3 — SOLVED. Our gating is correct; the prompt is fired into an activity that cannot show it.

**The log is unambiguous. All four gates are right and the branch is PROMPT:**

```
15:37:51.3700  [pause] resume/entered · pauseLock=held
15:37:51.3700  [pause] resume/pauseLock-held · ownIntentReturn=False sinceUnlock=17s
15:37:51.3700  [pause] resume/lock-stays-up · calling onForegroundReturned
15:37:51.3700  [pause] lock/onForegroundReturned · clearing authDeferred
15:37:51.3700  [pause] auth/maybeAuthenticate · uiReady=True pageVisible=True
                                                authAttempted=False authDeferred=False → PROMPT
```

So #460's latch works, `OnResume` reaches `onForegroundReturned()`, and `AuthenticateAsync`
IS called. **Nothing in our code is wrong.**

**What is wrong is WHEN.** One line later:

```
15:37:51.4064  Android OnResume - ensuring Node is running
```

`MainActivity.OnResume`'s own body runs **36 ms AFTER** we fired the prompt — because MAUI
raises `Application.OnResume` from inside `base.OnResume()`. We are prompting from the
**middle of the activity's onResume**, before it has reached the RESUMED state.

**And it never comes back.** There is no `lock/auth-returned` anywhere in the pause cycle;
the cycle ends with HomePage at +14275 ms, i.e. Damir typed the password. Compare cold start,
which works:

```
15:37:14.3462  [cold-start] ... → PROMPT
15:37:34.2105  [cold-start] lock/auth-returned          ← 20 s later: a real prompt, used
```

### ★ Why a PATTERN fails where a fingerprint would not

Damir authenticates with a **pattern**, i.e. the device-credential fallback
(`AllowAlternativeAuthentication = true`). androidx.biometric shows a fingerprint prompt as a
**DialogFragment** — that survives being called during onResume. Device credential is
different: it launches **`ConfirmDeviceCredentialActivity`, a separate Activity**. Android
will not start an activity on behalf of one that has not yet reached RESUMED — the launch is
dropped, and the `await` never completes. That is exactly what the log shows.

**This is the THIRD time MAUI's lifecycle mapping has cost a lock defect** — #442 (`OnSleep`
is raised from `OnStop`), #460 (`isInForeground` turns over at the wrong edge), and now
`Application.OnResume` firing before the activity is resumed.

**Fix (next batch, NOT taken here):** do not call `maybeAuthenticate` synchronously from
`onForegroundReturned`. Post it to a later edge — after `base.OnResume()` has returned, or one
UI tick later. ⚠ It must be verified with a PATTERN, not a fingerprint; a fingerprint would
likely have masked this bug in every previous round.

## 2. ★ F2 — the hypothesis is DEAD, and the instrumentation is why we know

The pause path's suspected missing call is a red herring. The bars **are** repainted, with the
**correct** colour, twice per lock:

`applyPlatformPageChrome` covers it. **Adding a `repaintSystemBarsFor` call — the "one-line
fix" the original hypothesis pointed at — would have done nothing at all.**

**The new hypothesis, and it is well supported.** `setEdgeToEdge` paints the status-bar strip
by setting the background of `MainActivity`'s **`android.R.id.content`** view
(`SPlatformUtils.cs:303-312`). The pause lock is a **MAUI modal**, and MAUI presents modals
**above** the content view. So the strip visible behind the modal is no longer the view we
paint — it is the **window** background, which `styles.xml:37` points at
`@layout/splash_screen`, base layer **#144576 — splash blue**. Every non-modal page looks
right because for those, content IS the top view.

**Next step, cheap:** confirm the modal's parent, then either paint the modal's own container
or set the window background to the page surface while a modal lock is up.

## 3. ★ F6 — SOLVED. Not the hysteresis, not the indeterminate frame. A BOGUS TARGET.

```
16:04:04.8846  [SCANDIAG] current=6028792 target=5333999 origin=0 lag=-694793
16:04:08.9026  [SCANDIAG] current=6028792 target=5334000 origin=0 lag=-694792
   … 40 seconds of a target ~700 000 blocks BELOW current …
16:04:41.0984  [SCANDIAG] current=6030868 target=6184643 origin=6030868 lag=153775
```

`determineHighestNetworkBlockNum()` returns a **stale, far-too-low** value for the first ~40
seconds after start, before a peer majority settles. Two consequences, and together they are
the whole of F6:

1. **The row hides.** The shell's caught-up test is `lag <= 20`. A negative lag satisfies it,
   so the row disappears — while the phone is 150 000 blocks behind.
2. **★ The progress is DESTROYED.** `HomePage`'s anchor logic reads
   `scanTarget <= scanCurrent + SCAN_CURRENT_LAG` as *caught up* and **retires the origin to
   0**. When the target corrects, the origin re-anchors to the *current* height — so the bar
   restarts from 0 %. That is exactly Damir's note: *"scan was at 19 %, I closed the app and
   restarted and now there's no scan."*

⚠ **A pre-existing pin caught a real bug in this very probe.** #453 forbids
`scanTarget - scanCurrent` because these are **ulong**; the audit's `blockGap` helper is the
only reason the log reads `lag=-694793` instead of `lag=18446744073708856823`. Unfixed, this
diagnosis would have been unreadable garbage.

**Fix (ours):** distrust a target below current — treat `target < current` as *unknown*, never
as *caught up*, in BOTH the shell's visibility test and HomePage's origin logic.

## 4. ★★ NOTIF — 3.4, 3.7 and 3.12 are ONE root cause, and it is a SECOND notification path

Damir, 3.7: *"I get the same notification as legacy; when I tap it, it takes me to a 1:1
rather than the group that originated it, but the group shows no messages."*
3.4: *"sometimes works, sometimes doesn't."*
3.12: *"sometimes a legacy type notification appeared besides the named notification."*

**All three are the OneSignal push fallback, which our mute never touches.**

`Spixi/Platforms/Android/SPushService.cs:242-258`:

```csharp
static void handleNotificationReceived(...)
{
    e.PreventDefault();
    if (OfflinePushMessages.fetchPushMessages(true, true)) return;   // ← our gated path
    ...
    e.Notification.display();                                        // ← RAW push, NO gate
}
```

When `fetchPushMessages` succeeds, the real message is pulled over Ixian and goes through
`Node.addMessageWithType` — where NOTIF-1's mute applies, and it works. When it **fails**
— push server unreachable, registration fails, a parse error, or the HTTP call throws
(`OfflinePushMessages.cs:91-121`) — the code falls through and displays the **raw OneSignal
notification**, which:

* **ignores every mute and the global master** → 3.7 fails, and 3.4 is "sometimes";
* carries no sender name and none of our formatting → 3.12's *"legacy type notification"*,
  and it can appear **beside** ours because the two rows have different ids;
* carries `AdditionalData["fa"]` = **the SENDER's address, not the group's** → tapping it
  opens the 1:1 with the sender rather than the group. **Damir observed exactly this.** And
  the group is empty because the message was never fetched.

**This is why NOTIF-1 tested as a failure despite being correct.** The fix I shipped is in the
right place; there was simply a second door.

**Split of the fix:**
* **OURS:** gate `e.Notification.display()` on the global master and on the per-1:1 mute for
  `fa`. Covers 3.4, 3.12 and the 1:1 half of 3.7.
* **⚠ NOT ours:** a group push carries the sender's address, so the recipient cannot tell
  which group it belongs to and cannot apply the group's mute. The push payload needs the
  group address. That is a push-server / protocol change — **BE**.
