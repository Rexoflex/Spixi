## What changed and why
- **Why the drop exists today.** `App.OnSleep` drops the spare on every non-Windows target (`App.xaml.cs:1432`, comment `:1416-1424`). The reason is NOT a security rule: the spare holds no chat. It is a reliability belt against a hidden WebView whose own content process died while the app lived and would show blank at the 400 ms backstop. That is an Apple mechanism (WKWebView / jetsam); no renderer-death handler exists in `Spixi/**` (grep, 0 hits; reason doc § 1).
- **Why keep it on Android.** After 60 s in the background no spare existed in 15 of 15 opens (286–296 ms against 97–114 ms on a spare; P39). On Android all WebViews share one renderer, so a kept spare cannot be the only dead WebView (reason doc § 2). The price is memory: about 15 MB renderer PSS, now held for up to 3 minutes in the background.
- **The sleep site.** Under `#if !WINDOWS`: `spareKept = SpixiFlags.SpareKeepShortSleep && SpixiContentPage.keepSpareAtSleep(isLockEnabled() || isLockScreenActive)` (Android only); not kept → today's `dropSpareChat("sleep")` (`App.xaml.cs:1425-1433`, the `spareKept` line `:1428`). The whole block stands AFTER `isInForeground = false` (`:1411`; #46 r2 R2-5), so a chats flush already running cannot take a P39 re-arm in between. Switch OFF, iPhone and Mac = the drop as before; Windows never drops at sleep.
- **What is kept.** `keepSpareAtSleep` (`SpixiContentPage.cs:2103`) keeps a spare only when it is READY (`spareShellBooted`), no chat is staging, the app lock is off and no lock is up or staging (`SpareKeepRules.atSleep`, `SpareKeepRules.cs:29`); else drop. From then on it is UNPROVEN (`Kept`): the statics `spareKeepOp / State / AtTick / AtUtc / ProofSeq` live under the preload lock (`:2096-2100`).
- **Fail closed at the claim.** `pushSpareChat` begins with `dropSpareIfKeptUnproven()` (`:2350`, body `:2172`): a kept spare whose state is not `Proven` is dropped and the open takes the cold path (`SPARE_WHY_NONE`). A tap before the proof answers is cold, never a blank page (csh `model_sleep_return_tap_at_once_is_cold_and_drops_the_spare`).
- **The return.** `App.OnResume` calls `spareKeepOnResume()` (`App.xaml.cs:1164`; body `SpixiContentPage.cs:2132`): the limit first (3 min = `LimitMs`, `SpareKeepRules.cs:22`; the larger of the monotonic and wall clock; a clock that went back = over, `:40`), then the proof is POSTED so it runs after OnResume's lock decisions. The post is real since #46 r1 A-2: `_ = Task.Run(() => MainThread.BeginInvokeOnMainThread(() => startSpareKeepProof(op)))` (`:2168`). `OnResume` is already the main thread, and `BeginInvokeOnMainThread` runs inline there (`Platforms/Android/MainActivity.cs:580-582`), so the hop through the pool is what moves the proof to a later turn.
- **The proof.** `startSpareKeepProof` (`:2197`) evaluates `document.readyState` on the spare's OWN WebView (`:2221`; the expression `checkIfPageLoaded` already uses, `:915`). It reads one DOM state word and writes nothing; no chat function, no push, no log. `"complete"` within `ProofDeadlineMs = 1000` and no lock → `Proven` (`SpareKeepRules.afterProof`, `:89-100`); anything else (no answer, late, wrong, lock up) → drop. Only the ANSWER sets `Proven` (`finishSpareKeepProof`, `:2232-2255`); the deadline passes `null`. The lock test that counts is the one at the ANSWER (`:2235`, `appLockUpForSpareKeep() || isLockStaging()` plus `modalOverlayOp` at `:2248`); the test at proof start (`:2199`, `:2209`) is kept as well. Who reads the answer: `finishSpareKeepProof` → `afterProof` only; it is compared and discarded.
- **Timers can only drop (L157).** The 3-minute timer (`:2126`, `dropKeptSpareAtLimit` `:2258`) and the 1 s proof deadline (`:2222`) both end in `dropKeptSpare` or a no-op, never in `Proven`. The one drop of a kept spare is `dropKeptSpare` → `dropSpareChat("sleep")` (`:2276`, call `:2292`), the existing word: no new log word. Every existing drop (`theme`, `language`, `reload`, `lowmem`, `stop`, `host`) still drops a kept spare because it stays in `spareChatOp`.
- **With P39 (`SpareRearm`) ON.** A proven spare needs no re-arm. Every drop above uses `sleep`, so a dropped one re-arms through P39 (warm at about +1.8 s, behind the P38 idle gate).
- **Flag.** Int pref `flagSpareKeepShortSleep` (`SpixiFlags.cs:31`, `:100`, `:145`, `:180`), absent = OFF, `PerfB1Rules.effectiveOptIn` (`PerfB1Rules.cs:12`) = `devMode && stored == 1`; `[FLAGS] … sparekeep=…`. Dev switch `ixian:devflash:sparekeep:<0|1>` (`DevPage.xaml.cs:159`). OFF: `keepSpareAtSleep` is never called, `spareKeepOnResume` and `dropSpareIfKeptUnproven` return at once → the old drop.
- **Leaving dev mode (#46 r1 B-1 / S-5).** `ixian:disableDevMode` (`HomePage.xaml.cs:1852`) removes the four `SpixiFlags.PerfB1DevKeys` (`:1862`) and calls `SpixiFlags.leaveDevMode()` (call `:1866`; `SpixiFlags.cs:112`), which sets `SpareKeepShortSleep = false` in the running process, BEFORE `dropSpareChat("devmode")` (`:1869`). The account wipe is the second way out of dev mode: `SettingsPage.wipeEverything` calls `SpixiFlags.leaveDevMode()` (`SettingsPage.xaml.cs:1848`) right after `Preferences.Default.Clear()` (`:1846`) and `WalletPassStore.clear()` (`:1847`) (#46 r2 R2-1). On both ways the opt-in is OFF at once; a stored 1 does not survive. "Cannot be ON outside dev mode" holds immediately, not only at the next start.
- **Debuggable dev builds.** Dev builds are debuggable (the walk handoff saw `pkgFlags` DEBUGGABLE on the Release dev build), so `adb shell run-as` can write the preference file directly. That holder already has the app's trust level. A stray stored value fails safe: `effectiveOptIn` needs exactly 1 and dev mode; a wrong type throws into the catch and the defaults apply.

## Threat → rule → proof
| What could go wrong | What stops it | Proof |
|---|---|---|
| Chat content in a kept spare (the PARAMOUNT isolation invariant) | Unchanged: the kept page is the blank spare with no friend; keeping adds time in the background, not a data path; it is kept only READY and with no chat staging | pin `c-spare-keep` (`keepThroughRule`); P16 |
| A kept spare shown with the app lock on, or a spare kept while locked | Not kept if the lock is enabled, up or staging; the proof refuses and drops while a lock is up (`App.isAppLockActive`, in-place lock) | csh `a_lock_drops` · pin `SLEEP`, `PROOF` (`lockUp`) |
| A dead spare handed to a chat open (a blank chat) | Unproven = no spare; `Proven` only from an in-time `complete` answer; every other way out is a drop | csh `unproven_is_not_usable`, `proof_late_or_wrong_is_not_usable` · pin `CLAIM` (`claimFirst`, `claimChecksProven`), `PROVEN` |
| A timer frees a spare that was never proven | The timers can only drop | csh `the_background_timer_only_drops` · pin `OUT` (`timerOnlyDrops`) |
| A kept spare lives for ever | 3-minute limit, both clocks; a clock that went back = over | csh `the_limit_just_under_at_over_and_a_clock_that_went_back` · pin `RESUME` (`limit`) |
| The JS read leaks data or runs more | One constant expression on the spare's own WebView; the answer is compared with `"complete"` and dropped; no log, push or verb in the region | pin `PROOF` (`ownWebView`, `noLogNoPush`) |
| A stale answer settles a newer cycle | A sequence number voids an older cycle's answer | pin `OUT` (`settledOnce`) |
| The proof starts inside OnResume's turn, before its lock decisions | The post goes through `Task.Run` first, so the main-thread post is a real one | pin `POST` |
| A lock comes up between the proof's start and its answer | `finishSpareKeepProof` tests the lock again at the answer, and that test decides | csh `a_lock_drops` · pin `PROOF` (`lockUp`) |
| Switch OFF differs from today | The flag is read first at all three entry points; OFF = the old drop | csh `switch_off_drops_at_sleep` · pin `SLEEP` (`sleepSite`), `CLAIM` (`offIsOld`) |

## NOT proven
- ⚠ C# UNCOMPILED for Android. The csh harness runs the pure rule and a model of the call order; the pins read source text.
- **What Android does when the shared renderer dies in the background is platform behaviour, not proven here.** The reason doc argues the app process dies with it (no `onRenderProcessGone` override exists), so the next tap is a cold start; this is reasoned from the tree and Android's documented default, not observed. The proof answers only that the document's renderer runs JS at the return; it is not a proof of paint.
- No device number: whether the open falls back to about 100 ms after a short sleep, and what holding about 15 MB renderer PSS for up to 3 minutes costs (a slightly higher chance the system ends the app), are not measured. The keep rule: a switch that does not measurably help on the device is removed.
- **Residual (#46 r1, not closed).** `dropKeptSpare` re-checks `spareChatOp == op` under the lock, leaves it, and then calls `dropSpareChat("sleep")`, which drops WHATEVER is in the slot: a fresh spare warmed in that window would be dropped (and, with P39 ON, re-armed). After `leaveDevMode` the stale `spareKeepOp` can also keep a reference to one disposed page for the rest of the process, not only until the next sleep. Both cost speed or a few bytes, never a wrong page.
- Whether a STORE-shape Android build is debuggable was not checked (nothing in this batch touches it); for the main chat.
- iPhone and Mac keep the drop; the Apple phase needs a `webViewWebContentProcessDidTerminate` handler (P-15) first.

## How to switch it off
It is OFF unless dev mode is on AND the stored value is 1. To turn it off: `ixian:devflash:sparekeep:0` (no row on the Developer screen in this batch) → restart.
