## 2. What N66 was — read before you touch theming again

`App.xaml.cs` pinned `Current.UserAppTheme` to a concrete value at boot, and the
OS-flip handler pinned it again as its own first line. MAUI resolves
`Application.RequestedTheme` to `UserAppTheme` whenever that is not
`Unspecified`, and it drops `RequestedThemeChanged` when the resolved value does
not change. **The handler disabled itself the first time it ran**, so the
`SpixiThemeName` re-bake, `setEdgeToEdge`, `reloadAllPages` and the #315 parked
dispose had all been dead for months.

`UserAppTheme` now stays `Unspecified`, `ThemeManager` resolves "automatic" from
the platform theme (`isPlatformDark()`), and the revived handler returns early
unless the appearance is System.

★ **N71 is what reviving it exposed.** The revived path RELOADS where the
working explicit-pick path PUSHES. Damir's F5 found four symptoms of that one
root: Account keeps the old theme after Light → System · an OS flip ejects the
user from the page they are on (Contributors → Chats) · the chats screen always
reloads · the Account top bar recolors a beat late. **`settings.html` has NO
`setTheme` handler at all**, and eleven other shells are in the same state (the
W1/#336 class). The fix is one item: make the OS-flip path do what the pick path
does, and give every live shell the handler. **Not this session.**
