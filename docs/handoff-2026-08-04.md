## The four findings

### F1 — iOS scan is completely dead. PRE-EXISTING, C#-side, not batch A. ★

**Symptom:** the scanner won't scan at all. **Torch works fine.**

That torch detail is the diagnosis. Torch is applied to a *live* `MediaStreamTrack`, so the camera
is acquired and running — permission is fine, `getUserMedia` succeeded, the track is alive. What's
missing is the *video rendering*: html5-qrcode decodes by drawing the `<video>` element onto a
canvas, and if WebKit refuses inline playback there is nothing to draw, so every frame decodes as
empty. Zero scans, working torch.

**This is iOS-49, already logged in DECISIONS #293 and never finished.** That row says it
explicitly: *"Permission now works; the PREVIEW IS STILL BLACK — remaining half is inline playback…
`AllowsInlineMediaPlayback` must be set on the configuration AT CONSTRUCTION."*

Verified in the tree: `MediaCaptureUIDelegate` is installed
(`Spixi/Platforms/iOS/iOSWebViewHandler.cs:71,119`) — that was the #293 half that landed. There is
**no `AllowsInlineMediaPlayback` anywhere in the repo** (grep: zero hits).

**Why it needs C#, and why it can't be patched where the current code lives.**
`AllowsInlineMediaPlayback` is a property of `WKWebViewConfiguration`, and a `WKWebView`'s
configuration is **immutable after construction** — a copy is returned at runtime, so setting it
later silently does nothing. `iOSWebViewHandler.ConnectHandler(WKWebView platformView)`
(`:113`) receives an already-built view, which is too late. The fix is to override
`CreatePlatformView()` on `iOSWebViewHandler`, build a `WKWebViewConfiguration` with
`AllowsInlineMediaPlayback = true` (and `MediaTypesRequiringUserActionForPlayback = None`), and
construct the `WKWebView` from it.

**Consequence for batch A:** A8 (scan zoom) is built and cannot be verified on iOS until this
lands. It is *not* known-broken — it is unobserved. Don't mark R12 closed.
Also: the `playsinline` attribute on the video element is a second, FE-side requirement — check
the vendored html5-qrcode sets it (`Spixi/Resources/Raw/html/js/html5-qrcode.min.js`) once the
native half is in; if it doesn't, that's a small shell-side patch.

**Priority: this is the highest-value fix on the list.** Scan is how contacts and addresses get
into the app on the platform Damir is testing on, and it has never worked there.

### F2 — Pinch-to-zoom document-zooms every screen except chat. NEW, zero-C#.

**Symptom (Damir):** on wallet, apps and account you can pinch and zoom the whole screen like a
web page. It should only work in chat, where pinch changes the *message text size* — the same
preference Account → Chat appearance writes.

**Cause, and it's a one-line-per-file sweep.** `src/shells/chat.html:10` carries a scale clamp:

```
width=device-width, initial-scale=1, minimum-scale=1, maximum-scale=1, user-scalable=no, viewport-fit=cover
```

**Every other shell (17 of them) has no clamp** — just `width=device-width, initial-scale=1,
viewport-fit=cover`. Without it WKWebView owns the pinch and raster-zooms the document. The chat
clamp was added 2026-07-29 *specifically so the custom pinch-to-text gesture could exist*
(`chat.html:884-918`), and the fix was never swept to the other shells.

**Fix:** add the same clamp to the other 17 shells. Chat keeps its gesture handler; nothing else
needs one.

**Belt worth considering (2 lines of C#, covers the LEGACY pages too):** in
`iOSWebViewHandler.ConnectHandler`, next to the existing `ScrollView` settings at `:121-123`:
`platformView.ScrollView.MinimumZoomScale = 1; platformView.ScrollView.MaximumZoomScale = 1;`.
The redesigned shells scroll inner containers, not the WebView's own scroll view (which is already
`ScrollEnabled = false`), so this costs nothing — and it also covers `wallet_send.html`,
`apps.html` and the other still-legacy pages that the FE sweep won't reach.

⚠ **One decision this forces, don't ship it silently.** `--chat-text-scale` is **chat-only** — the
Account setting is literally labelled "Message text size" and only `message-bubble.css` consumes
it. So clamping every screen removes the only remaining way to enlarge text on wallet/apps/account.
Three options: (a) clamp everywhere and accept it, (b) clamp everywhere *and* extend the text-size
preference app-wide (a real job — touches every component's type scale), (c) clamp now, log
app-wide text scale as a follow-up. **Recommend (c)** — it matches Damir's stated intent and
doesn't block on a type-scale project.

### F3 — Wallet Share must never carry the `:send:<amount>` payload. Zero-C#, small.

**Damir:** *"the request shouldn't copy the `:send:1` since it's not valid — we can't share a
request for a specific amount yet, so that needs to go out."*

Current behaviour after A10: with an amount entered, Share copies `address:send:1` and toasts
"Copied". That format is a **Spixi-internal QR payload** (`setSendAddress` parses it) — it is
meaningful to a scanner, gibberish in a message to a human, and the amount-request feature it
implies isn't shippable yet.

**Fix:** `onShare` in `src/shells/home.html` should share the **bare address, always**, regardless
of whether an amount is entered. That collapses the amount-gate branch added in A10 — the gate
existed to stop the amount being *silently dropped*; Damir's call is that the amount shouldn't be
in the shared text at all, which makes the whole branch unnecessary. The QR itself keeps encoding
`address:send:<amount>` (that path is scanner-to-scanner and still correct) — this is only about
what leaves the app as text.

Worth deciding at the same time: should the **Share button** still be offered while an amount is
entered, given it will share something that doesn't include the amount? Options: share the bare
address anyway (simplest, slightly surprising), or hide/disable Share while an amount is set. The
second is more honest; it's a one-line gate either way.

### F4 — Presence goes stale: a contact shows online for ~2 min after they quit. NOT FE.

**Damir:** offline contacts render correctly; the most-recently-online one keeps showing online
~2 minutes after that person closed Spixi, and a Spixi restart resets it.

**The A4 render is correct** — it faithfully shows what C# pushes. The staleness is upstream:
`Node.cs:418-455` reports online only when a `PresenceList` entry exists **and**
`friend.relayNode != null`, and it goes false only when the PL entry **disappears** — i.e. on
network expiry, not on the peer quitting. `StreamProcessor.cs:217-222` also force-sets online on
any inbound stream message. So "online" really means *"was announced in the presence list and
hasn't expired yet"*.

The restart-clears-it detail fits exactly: a fresh process rebuilds the PL from the network rather
than carrying the stale entry.

**This is a BE / Ixian-Core item, not a shell fix.** It matters because a green dot is a trust
signal — a user messages someone the app says is online and gets nothing. Two ways out, both
BE-side: shorten presence expiry / send an explicit offline announce on clean shutdown; or soften
the FE claim (a "last seen" treatment rather than a binary dot) — which would be an FE job but
needs a timestamp the bridge doesn't currently carry.

**Log it for the BE engagement. Do not "fix" it in the shell** — there is no honest signal to
render.
