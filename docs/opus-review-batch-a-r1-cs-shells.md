## VERIFIED CLEAN

Everything below was checked against source and holds.

- **Verb placement + collisions.** The three new branches sit at `HomePage:536-547`, ABOVE the first `Contains()` branch (`ixian:qrresult:` at `:548`) — the #216/#393 rule. All use `StartsWith` + `Ordinal` + a trailing colon. No other `ixian:remove*` / `ixian:sharedGroups` / `ixian:openChat` branch exists on HomePage, and `onNavigatingGlobal` (`SpixiContentPage.cs:2687-2706`) only matches `appAccept:` / `appReject:` / `hangUp:` — no swallow. `ContactDetails` uses `Equals("ixian:sharedGroups")`, a different page, no collision.
- **Argument transport.** `Utils.sendUiCommand` base64-encodes EVERY argument (`escapeHtmlParameter` → `Convert.ToBase64String`, `Utils.cs:36-39,246`); the raw fast path is gated on `supportsRawDataUriArgs` AND a strict `data:…;base64,` whitelist that excludes quotes, backslashes and separators. A group nickname containing `'`, `\`, CR/LF or `${` cannot break the injected JS call. Both shells render the pairs with `textContent` (`chat-info.js:832`, no `innerHTML` on the shared-groups path).
- **Address parsing.** `chat.address` is always `friend.walletAddress.ToString()` — Base58Check, which has no `:`. `LastIndexOf(':')` therefore splits the flag correctly, and a payload with no flag (`sep == -1`) degrades to `addr = p`, `leave = false`. `new Address(addr)` throws only on garbage and every call site is inside `try/catch`, so `onNavigating` never throws (the A-4 rule). `leave` is a literal `"1"` test — anything else is `false`.
- **Thread safety / re-entrancy.** `SContacts.sharedGroups` snapshots `FriendList.friends` into a local (`friendsRef`) before locking — the ContactDetails loop-n4 fix, correctly carried over — and **releases the lock before returning**. `removeContact` therefore holds NO lock when it calls `leaveGroup` → `FriendList.removeFriend` → `isFriendInGroup` (which takes the same lock). No deadlock, no re-entrancy. The leave loop iterates `pairs`, a flat snapshot `List<string>`, so `FriendList.removeFriend` mutating `friends` inside the loop is safe. Lock ORDER (`friends` → `users.hasUser`) is identical to Core's own `isFriendInGroup` (`FriendList.cs:412-426`).
- **Group-in-group refusal.** `FriendList.removeFriend(group)` is NOT refused: `isFriendInGroup` only matches entries with `type == FriendType.Group` whose `users` contain the address, and a group is never a member of another group. Confirmed at `FriendList.cs:418-419`. The leave-first ordering is therefore sound.
- **`updateScreen()` re-push.** Both handlers call it unconditionally; `HomePage:2830-2835` runs `loadChats()` + `loadContacts()` when `UIHelpers.shouldRefreshContacts` is set, which `SContacts` sets on every success path (`:85,:129,:147`). The deleted row cannot resurrect: `deleteHistory` nulls `metaData.lastMessage` (`Friend.cs:535`) and `getFriendMessageHelper` returns null for that (`HomePage:2074-2079`), so `loadChats` emits no row. `updateScreen` is wrapped in its own try/catch, so a throw cannot escape into `onNavigating`.
- **Sequence, step 1 vs step 2.** The history verb IS sent before the contact verb (`chats-row-menu.js:354` then `:357` via the sheet confirm). `removeFriend` also deletes messages (`FriendList.cs:438`) — a harmless double delete. Tapping "Keep contact" at step 2 leaves the history already gone, and step 1's modal states that plainly ("Delete chat?" + a checked, disabled "Delete chat" row).
- **Blocked/refusal honesty.** `removeContactResult`/`removeHistoryResult` un-tombstone on anything but `"ok"` (`home.html:3321,3334`). On `"blocked"` nothing was destroyed, `shouldRefreshContacts` is correctly NOT set, and the contact remains in the directory — no stale directory state to refresh.
- **Push definition (#258).** `setSharedGroups`, `removeContactResult` and `removeHistoryResult` are all inside the `handlers` literal passed to `bridge.exposeAll` (`home.html:3307-3337`, `:3512`), so C#'s bare-global push can never throw before the dispatcher.
- **`ixian:openChat:` on a wide layout.** `popPageAsync()` is overlay-aware: it finds the page in `overlayStack` and calls `closeOverlay` (`SpixiContentPage.cs:2859-2872`), so a pinned detail pane closes correctly rather than popping a native page. It is exact parity with the existing `ixian:chat` branch (`ContactDetails:304-319`), and it is gated on `FriendList.getFriend(targetAddr) != null` — an unknown address is a no-op.
- **`sendLeave` parity.** `StreamProcessor` extends `CoreStreamProcessor` (`Spixi/Network/StreamProcessor.cs:21`), so `SContacts`' `CoreStreamProcessor.sendLeave` and `SingleChatPage`'s `StreamProcessor.sendLeave` are the same static. The group and bot bodies are byte-for-byte the #248 bodies.
- **Sheet lifetime guards.** `setRemoveSheetGroups` / `setRemoveSheetResult` both require `isConnected` AND an address match, so a late answer for another peer is dropped (`chats-row-menu.js:305,315`). `remove.disabled` is true while `groups === null` — no blind removal.
- **Group rows.** `openRemoveContactSheet` decides its copy from the shell's `chat.type`, but C# decides the BODY from `friend.type`/`friend.bot`. A row whose CH1 kind never arrived still takes the correct leave path. Good separation.
- **chat.html item 4 (hypothetical, the surface is unreachable — see A-10).** `refreshChatInfo` uses `replaceChildren`, so a member row IS replaced under the finger — but the debounce strictly IMPROVES this (once per burst instead of once per animation frame). The member sheet attaches to `overlayHost = document.body` (`chat.html:2046,2486`) and survives the rebuild. `rosterLanded()` is a no-op when `rosterLoading` is false, so a non-group chat is unaffected. Focus is lost on every rebuild (`replaceChildren`) — pre-existing.
- **Build inclusion.** `Spixi/Utils/SContacts.cs` is picked up by the default SDK glob (the only `Compile Remove` entries are the per-platform folders, `Spixi.csproj:282-297`).
- **Built output is in sync.** `Raw/html/index.html`, `contact_details.html` and `chat.html` all contain the new code — the shells were rebuilt.
- **No money path touched.** `SPayments`, signing, confirm and the wallet verbs are untouched by this batch. The one money adjacency is A-3's surviving info pane.
