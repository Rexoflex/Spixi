Second-device warning · dropped from DT-1

Shows through the existing showWarning bannerText fixed, Damir's copyStatus dropped (Damir, Q2) → BE ask

The planned banner, with Damir's fixed text. The discovery (Ixian-Core 097341a) found that Spixi does not receive the presence of its own address from other devices today, so the rule has nothing to read. Damir (Q2): drop C from DT-1; record the 14:21 decision and a BE ask. The banner below is kept for later.

Finding (read in the tree) 1 · No subscription to our own address. A client subscribes to keepalives only for its friends (CoreNetworkProtocol.subscribeToEvents, the friend cuckoo filter, :1312–1323). The node forwards a keepalive to a client only when the client is subscribed to that address (NetworkServer.cs:799). Spixi never asks for its own presence: getPresence2 goes out only for an unknown wallet, from inside receiveKeepAlive.
2 · Core erases the other-device entries of our own address. When a keepalive for OUR wallet comes from a device id we do not hold, Core resets our entry to this device only (PresenceList.cs:766–771, also :687–692, curNodePresence.addresses.Clear()). A full presence update (updateEntry, :172–219) would add the other device, but nothing asks for one.
3 · The banner cannot clear itself. In the home shell only a connectivity text and "" have a clear path. Any other text stays until the user closes it (home.html:4812–4842). "It clears when the other device goes quiet" needs a new push or a shell change.
So C needs a NEW network request, and Core behaviour we do not own. The DT-1 STOP rule applies. No Core change.
D

Chat info grows the window · #1179 (b) · Q3

Windows AppWindow.MoveAndResize against DisplayArea.WorkAreaMac UIWindowScene.RequestGeometryUpdate (can be refused → squeeze)Saved size never includes the pane (#1073)

Today chat info opens as a 360 px column beside the chat and squeezes the conversation. With the change, a restored window (not maximised, not full screen, not snapped) grows by the pane width when the work area has room ON THE RIGHT, so the conversation keeps its width. No room on the right → squeeze as today (Damir, Q3). On close it shrinks back by the same amount, only if the user did not resize or move the window in the meantime. A 1920 × 1080 screen, a 1180 px window.

Found in the tree Motion. Today the pane arrives with the "width" motion: column 2 runs 0 → 360 in 220 ms (HomePage.xaml.cs:202–212). If the window grows by 360 at the same time, the conversation first gets wider and then narrower. The build sets column 2 to the full width at once when it grows (the new window area is the motion), and keeps the motion of today for the squeeze.
Save rule (Windows). The size is saved in the window mapper closure (Platforms/Windows/App.xaml.cs:173–223) on every Restored size change. The grow must tell that closure the pane amount, so it saves the size without the pane, also when the app closes while the pane is open. B also edits this file, so B and D run in order, B first.
Mac save. Spixi saves no window size on the Mac; macOS restores the window frame itself. If the app quits with the pane open, macOS can bring back the grown frame. Walk row DT-MAC-RESTART checks it.
Follow. The pane follows a chat switch (#1179 a). The window stays grown while it follows. It shrinks only when the pane closes.
