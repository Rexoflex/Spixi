## 2. THE FIX LIST — start here, in this order (F-3 is DEFERRED, see below)

### F-1 🔴 The backup nudge fires on an UNACCEPTED contact — ROOT CAUSE FOUND

Damir: a nudge right after joining the Spixi community, and a nudge on a fresh
account after scanning a QR, **before** that contact accepted.

`Friend.approved` **defaults to `true`** (`Ixian-Core/Streaming/Friends/Friend.cs:196`,
ctor `:233` — `bool approve = true`), and every OUTGOING request in this app adds
the friend without passing it: `HomePage.joinBot:1378` · `ContactNewPage:195` ·
`SingleChatPage:1426` · `SpixiContentPage:2389`. So `approved` is true from the
moment you SEND a request. Only an incoming request sets it false.

The `#393` MAJOR-3 guard therefore does nothing. **The real signal is
`friend.state == FriendState.Approved`** (`Friend.cs:159-166`: RequestSent ·
RequestReceived · Approved · Ignored · Unknown) — the same predicate `#275` uses
for the composer lock.

Fix in `HomePage.hasBackupWorthyAsset`: count a friend only when
`friend.state == FriendState.Approved && !friend.pendingDeletion && !friend.bot`.
Keep the balance leg. Re-pin the smoke assertion on the STATE, not on `approved`.

## 6. Group chat — answered, no work owed here

Damir asked why group members who are not contacts cannot see each other's
messages. Investigated in Ixian-Core (read access granted this session):
**inherited, not introduced.** `Streaming/GroupChat.cs` and the group send path
landed in Core on 2026-05-17; our fork point `0e85a4b8` is 2026-06-16.
Mechanism: messages are encrypted per recipient with keys from the contact
handshake (`CoreStreamProcessor.cs:176`/`:246`), so `sendGroupMessage:354-391`
skips a participant who is not your contact and falls back to sending ONLY to
the group creator, who re-broadcasts (`:394-406`, `:826-874`). The design works,
but the creator is a permanent relay: nothing flows between two strangers while
the creator's app is not running. Cap is 10 participants.
🟡 Latent trap for the BE engineer: `GroupChat.CreateGroup:44-55` stores real
public keys, while `JoinGroup:92-100` stores the ADDRESS in the same publicKey
slot on every joiner. Harmless only because `replaced_sender_address = true` is
commented out for private groups (`CoreStreamProcessor.cs:816`).
