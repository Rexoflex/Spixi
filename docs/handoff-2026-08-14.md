**iOS-67 — FAB → contacts picker is unresponsive on iOS, then exits to the chats list.**
Logged on the PC in `docs/ios-sim-findings.md`, which the reset above will discard.
Re-log it there or here.

Report: tap the FAB to start a new chat. The contact list appears but does not respond
to taps. After a few more taps the surface closes and the user is back on the chats
list. iOS device only. Not seen on Android or Windows.

Hypothesis: the taps are not reaching the rows. "Dead, then closes after N taps" is the
signature of taps landing on the SCRIM, not the content — each tap is a light dismiss,
and the overlay closes on the one that registers. WebKit builds a new containing block
for `transform`, `filter` and `backdrop-filter` where Chromium does not, so a layer that
sits correctly on Android can sit ABOVE its own content on iOS.

The decisive test — Safari → Develop → AI15 → Console, with the picker open:

```js
document.elementFromPoint(innerWidth / 2, innerHeight / 2)
```

- a `.c-contacts__*` row → stacking is fine, the fault is in the handler.
- a scrim or overlay element → confirmed; the fix is a stacking correction scoped to
  the picker.

## ★ FIRST TASK TOMORROW — settle whether the delay is real

Damir tested #343 on Android and reported two things: no press feedback, and the delay
unchanged or worse.

**The press-feedback miss has a proven cause and is fixed in this commit.** `base.css`
loads BEFORE every component stylesheet, and `.c-chatlist-item` sets
`background: transparent` at the same specificity, so the press rule lost on source
order and the tint never painted. The rules now carry an `html:root` prefix (0,2,1),
which beats the component's `[aria-current]` and `:active` rules from anywhere in the
cascade. There is a mutation-tested pin on the prefix.

**The delay report is unresolved, and there are two possibilities. Establish which
before changing any code.**

1. **The build Damir tested may not have contained the frontend changes at all.** His
   two symptoms — no press feedback AND no speed change — are exactly what an
   un-rebuilt `Raw/html` looks like. The tell takes five seconds: tap a chat row and
   watch the first frame. A top bar and a composer bar, empty, then messages = the new
   frontend is live. A blank canvas or the old spinner = it was never in the build.
2. **The delay is real and my model of it was wrong.** `Config.messagesToLoad` went
   100 → 25 in this commit. If that changed nothing, then the ~100 per-message
   `EvaluateJavaScriptAsync` crossings are NOT the dominant cost, and the remaining
   suspects are the ~1.4 MB document parse per screen and the C# side.

**Then measure, do not guess.** This is rule #294 and it applies to the assistant too.

- **Build Release first.** Everything so far was Debug, and iOS additionally runs with
  `UseInterpreter=true`. Judging performance from a Debug interpreted build is not a
  measurement.
- **One trace:** phone connected, `chrome://inspect` in Chrome on the Mac, inspect the
  Spixi WebView, Performance tab, record, open a chat, stop. That splits the time
  between document parse, script execute, and waiting for data. Fix what the trace
  names.

**One honest risk in this commit:** the boot spinner now waits 300 ms. If the instant
chrome does NOT render, the user sees a blank canvas with no spinner where there used
to be one — which would feel worse. That is a one-line revert
(`.chat-boot__spinner` in `src/shells/chat.html`).
