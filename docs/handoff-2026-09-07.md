### The three MAJORs that mattered

★ **We widened the remote-media auto-fetch from two hosts to all of them.** The baseline
auto-loaded an `<img>` only for an anchored `^https://<label>.(tenor|giphy).com/…`. The redesign
accepted ANY host, over `http` or `https`, whose path ends in a media extension — on render, with
a gate that defaults ON and **no code anywhere that writes its preference**. The documented
opt-out did not exist. A stranger's first message took the reader's IP, user agent and read time.
⚠ The verifiers corrected the blast radius: Android and Windows already refuse the host at the
platform layer, so the live leak was iOS and MacCatalyst.

★ **A zip-slip in account restore.** The `#565` loop that heals Windows-made backups converts a
`\` in an entry name into a real separator. On Android, iOS and MacCatalyst a `\` is an ordinary
filename character, so `..\..\html\ll_chat.html` survives extraction as ONE legal file and is then
moved out of the extraction directory. It runs **before `verifyWallet`**, so an attacker needs only
the archive password. The verifier broke the stated impact chain and left the MAJOR standing on a
sharper primitive: unconditional `Directory.CreateDirectory` on the rebuilt path, which is a
permanent denial of service on the wallet path.

★ **iOS granted camera and microphone to mini-app content with no prompt.** The capture delegate
read neither `origin` nor `frame`, and the handler is registered app-wide. It is the iOS twin of
the inherited Android auto-grant. On the way, the fixer found the old mapping checked
`CameraAndMicrophone` against the VIDEO authorization, so a camera permission granted the
microphone.

## ★★ The #46 loop — six rounds, and the last two found a defect in the test infrastructure

Three disjoint auditors, then a fresh break-my-verdict reviewer per round. Every round after the
first returned NOT CLEAN.

**The pattern is the lesson.** The pin guarding the link-spoof fix was rebuilt three times and a
fresh reviewer defeated every version, because each one proved a NEGATIVE by matching ONE
SPELLING:

* r3 matched the keyword `if (` — one space — so a sink written `if(` was invisible.
* r4 matched the TYPE name `Browser` — a private helper, a local variable and `using static` all
  walked past.
* r5 matched the METHOD name `OpenAsync` — `UIApplication.SharedApplication.OpenUrl` and
  `SFileOperations.open` re-opened both security MAJORs with the suite green. `SingleChatPage`
  already calls that helper twice in the same file, and on Windows it is
  `Process.Start(UseShellExecute = true)`.

**The fourth attempt changed the design instead of the pattern.** Every external link the app
opens now goes through ONE gate, `Utils.openExternal`, and the pin proves a POSITIVE,
branch-scoped property: inside each `ixian:openLink:` branch the only call is the gate. That
killed reflection and a wrapper helper on its first run.

★★ **And the last two rounds found the stripper.** `stripCode` removed BLOCK comments before LINE
comments, so any `/*` inside a `//` comment opened a fake block comment and blanked everything to
the next `*/`. **17 live lines across four files were invisible to every negative sweep in the
suite** — three `ThemeManager` methods, a `launch-shell.js` constant, and the same line in both
generated bundles. A reproduction hid an OS-open primitive with `UseShellExecute = true` behind
two ordinary comments and the whole suite reported BASELINE OK. It is now a one-pass four-state
tokenizer; its pin compares it against three independent reference strippers, so pin and repair
share no premise; two sibling strippers were deleted in favour of it.

⚠ **That class is not closed file-wide.** 123 occurrences of the naive regex and 26 more local
strippers under 17 names remain across the suite and the scripts. Each can hide code from the
sweep that reads it. **That is the next session's first list.**

## ★ NEW, and it is Damir's report from the same day

**Android kills the app after about half an hour.** Settings shows 221 MB average, **511 MB
maximum**, on the Dev/coexist build. `#764` logged a 411 MB peak, so it has grown.

**Do not guess (#294). The instrument is one command:**

```
adb shell dumpsys meminfo io.ixian.spixi.dev
```

Read the FOOTER, not the total: the `WebViews:` count and the `Native Heap` / `Dalvik Heap` /
`Graphics` split. Take it at launch and again after the half hour that gets the app killed.

* `WebViews:` grows with use → a WebView leak.
* `WebViews:` stays 3–4 while Native or Graphics grows → not WebViews.

★ **The suspect, and it is code:** `SpixiContentPage.Dispose()` sets `disposed = true` and then
does ALL of its teardown — the handler disconnect, the `Source = null`, the layout removal —
inside `if (!Navigation.NavigationStack.Contains(this))`. A page that is on the stack when
`Dispose` runs is marked disposed and keeps its platform WebView for ever. `#800`'s pre-warm
creates a chat page and re-arms it on every back-out, so that path now runs many times per
session where it used to run once, at a measured ~15 MB each.

**The free discriminator is item 5's own experiment**: `CHAT_SPARE_ENABLED = false`, rebuild, use
it for the same half hour. Kills stop → the pre-warm is the cause, and the fix is the disposal,
not the flag. Kills continue → the meminfo split says where to look next.

⚠ Rule out the heavy seed first (10 × 1000 messages). On that profile neither number means
anything.
