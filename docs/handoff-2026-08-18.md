### (g) The image data-URI cache has no limit — MEMORY

Found when Damir asked about the 338 MB in the Visual Studio diagnostics window.

`Utils.imageUriCache` (`Spixi/Utils/Utils.cs:53`) is a `ConcurrentDictionary`. It holds one
base64 string for each avatar path and each app-icon path. It has **no size limit and no
eviction**. Entries live for the life of the process.

The cost is higher than it looks:

- A 240 KB icon becomes a base64 string of about 320000 characters.
- A .NET `string` is UTF-16. Therefore that one entry uses about **640 KB** of memory.
- The entry stays after the user deletes the contact or removes the app.

This cache is correct and it is a real speed win. The #340 audit did not change it. But it
is unbounded, and it is the first place to look when memory grows on a device with many
contacts.

Possible actions, in order of cost:

1. Measure first (rule #294). Count the entries and the total characters at run time. Do not
   change anything before the number is known.
2. Remove an entry when a contact is deleted or an app is removed.
3. Put a limit on the cache. Use a least-recently-used rule.
4. Store the bytes, not the string. Build the base64 text only at push time. This removes the
   UTF-16 cost, but it adds work for each push.

**Mobile is the risk, not Windows.** Android and iOS end an application that uses too much
memory. A Windows desktop has no such limit.
