THE DESKTOP WALLET PANE (#896-#898) - Damir's report, traced and fixed the same day
"clicking through transactions they weirdly fade in in the pane, briefly revealing
the actual chat screen of some chat below", then: "there should be no flash at all
on desktop ... each other you open just changes instantly."

Three causes, and only the first was where I kept looking.

#896/#897 - WHAT WAS UNDERNEATH. The ixian:tab: sweep closed the Account pane, the
chat-info pane, the add-contact/add-app form pane and the tx detail - each by name -
and NOT the conversation. So a chat opened on Chats stayed live and pinned in the
detail column across the whole app. It closes now, gated off tab1 (a tap on the tab
you are already on, and home.html's Fix #8 boot echo, both arrive as ixian:tab:tab1).
The sweep was already making this argument: closeTxDetailOverlays is in that branch
because "the tx detail belongs to the wallet tab" (#263).
L6 had pinned the OPPOSITE ("a plain tab switch does NOT close the conversation"), so
that pin is INVERTED WITH ITS REASON rather than quietly flipped - L6 fixed the same
defect from a different trigger and scoped its negative before the wallet case existed.
closeChatOverlaysForContacts -> closeChatOverlays; 3 L6 pins re-based.

#898 - THE FLASH ITSELF, and both #896 candidates were WRONG. WalletSentPage.onLoad
ended with webView.FadeTo(1, 150): the page fading its OWN WebView in on every
construction, translucent for 150 ms, so whatever was pinned under the detail column
showed straight through. One line in the page, under two rounds of theory about the
overlay machinery and WebView2 compositing. The discriminator #896 proposed would have
split two mechanisms that were both wrong. Instant reveal now; the ctor's Opacity = 0
stays, and the shell's bridge.painted() already gates the present, so the ramp hid
nothing it was blamed for.

#898 - THE INSTANT SWAP. Every tap built a new page and a new WebView. An open detail
is REUSED: showTransaction(tx) swaps the field and re-renders, and onTransaction takes
that path before construct-and-present. The page draws entirely from that one field and
the shell commits a burst atomically (#289), so the new transaction paints in one frame.
The swap's risk is the latches, not the rendering - a stale isConfirmedDisplayed from a
CONFIRMED previous tx silently stops the 1 Hz poll for the new one - so that pin is
DERIVED from the class's own field declarations with a stated carve-out, and its
mutation proved it names the missing field.

Pin (1) failed on its own explanation before it was fixed: its negative sweeps for
FadeTo, and the docblock quotes FadeTo(1, 150) to say what was removed. Third time
that class appeared in one session (#771).
