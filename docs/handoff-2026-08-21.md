## 2. The five reported defects, and where each one actually was

**★ The lock (#442 → #454).** The shield was never the wrong colour or the wrong
z-order — it was **never drawn**. It is added while Android is already backgrounding the
app, so it enters the view tree and no frame follows. The last real frame stays, and that
is what the OS restores before any managed code runs. Nothing on the resume path could
have reached it. The lock now goes up at `OnPause`, while the window is still live, so
the last drawn frame IS the lock. Your two dials are honoured exactly: the 5-second
no-auth window is unchanged, and the recents thumbnail is untouched.

**G5 (#455).** Reported as a regression, and it is not one — `git show f10ff1ca^` makes
the share path byte-identical across the batch. The ladder was `navigator.share` →
clipboard, and **Android's WebView has no Web Share API**, so on the only platform this
button ships to the first rung was missing and the clipboard was the whole behaviour,
from the day it was written. `home.html`'s Share got a third rung (`ixian:share`);
settings.html got only the desktop gate. Both halves now match.

**#449.** Both ingest paths truncate correctly — which is exactly why it would not
reproduce from the row. The full address is put BACK at sheet-open time, by the roster
join in `enrichTx`: C# sends `friend.nickname`, and a contact created without a nickname
has its own address as its nick. The row and the header disagreed on one screen.

**#456.** "The scan is at 0%" is not the condition — a restored wallet also starts at 0%.
Nothing in the app could tell a new wallet from a restored one, so the create site now
records it. The gate is all three: created here AND no balance AND no rows.

**C4.1 (#457).** A push arrives a navigation round-trip after the first paint, so it
would have been a second flash. The shell is told in the first frame, through a carrier.

## 3. ★ What is now KNOWN that was not before

1. **A view added at `OnSleep` — or at `OnPause` — is not guaranteed a frame.** MAUI
   raises `Application.OnSleep` from Android's **OnStop**. Any "cover it on the way out"
   design that hangs off `OnSleep` is too late by construction. This cost three rounds.
2. **The pause lock fires biometrics into a backgrounded app if you let it.** `OnAppearing`
   runs during the pause and the WebView keeps executing, so `Plugin.Fingerprint` reached
   a paused activity: androidx.biometric cancels, which left an "invalid password" alert
   the user never asked for AND latched `authAttempted` — **fingerprint unlock dead for
   every pause lock**. Found by the audit, not by the build.
3. **The ModalStack and the NavigationStack cannot answer "is a lock up?"** They are blind
   to a STAGING lock (~1.3 s on every authorise flow) and to an in-place one.
   `CallPage.lockUp()` has known this since #270; the new code had to be taught it.
4. **#234 is real and it was one tap.** Confirm mode renders Cancel → `authSucceeded(false)`
   → `App.onUnlock`, **which ignores the bool**.
5. **`lock.html` does NOT inline the bundle** — `build-shells` co-locates it. A pin that
   read `lock.html` for a bundle symbol was red with the code present and correct.
6. **A C# syntax gate is possible here after all.** `tree-sitter-c-sharp` from npm parses
   the real grammar. Six batches shipped C# checked only by reading and brace counting.
