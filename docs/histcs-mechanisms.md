**Lock order:** `lock (messages)` (Core's list) → `gate`. Under the gate only `lock (fileRowsShown)` is taken (the empty branch, and ★ #46 r1 F2 the keep point's deferred add; no holder of that lock takes the gate or calls `loadMessages`), and no
code under the gate waits for the UI thread (★ #46 r3: the older page's pushes run on a pool thread, where `evaluateJavascript` POSTS and returns). ★ #46 r3: the new members take NO lock — `olderPostsPending` is an `Interlocked` / `Volatile` int (the increment sits under the gate, nothing waits on it), the marker and the deferral are `Task.Run` → `MainThread.BeginInvokeOnMainThread` posts that return at once, and the deferred re-run takes the gate and `lock (messages)` later in the usual order, from a fresh main-thread turn with nothing held → no cycle. Another load takes the gate alone, at its
start and its end, with no lock of `loadMessages` held → no cycle. A UI-thread load can wait on the gate only while the
older page pushes (a few posts, no build) — not for the read or the build.

**Why the counters AND the anchor:** a full load that started after the request reads a window that already holds the
older rows (the window grew before the task) and clears the log (`clearMessages`); if the older page pushed after that
clear, its rows would sit on top of a log that already holds them (a double at the seam). The rule makes the two
orders the only ones possible: the older page's pushes come wholly BEFORE the other load's start (then that load's
`clearMessages` wipes them and re-draws everything: correct), or the older page drops. A load that was in flight at the
request and ended before the check wrote a new anchor object → the reference check drops the page.

**★ #46 r3 — the two orders hold for the DELIVERIES, not only for the calls.** The gate orders the C# CALLS. The older
page's pushes are made on a pool thread, where `evaluateJavascript` POSTS to the main thread's queue; an OTHER load that runs
on the MAIN thread (the "Delete history" row of chat info → `SContacts.removeHistory` → `loadMessages()`, a channel switch, a
widening quote jump, `reloadScreen`) sends INLINE — its `clearMessages` / rows / `jumpToMessage` are delivered at once, AHEAD
of a kept page's pushes that are still queued. The gate said "pushed first", the shell saw "pushed last": the deleted page
could be drawn again. The rule now:
- A KEEP counts the page in `olderPostsPending` under the gate, before its pushes; its marker (the decrement) is POSTED
  behind those pushes (`olderPostMarker`), so the counter falls only when the pushes are delivered.
- Right after insertion (i) — the load is already counted by the gate (`beginLoadScope`), directly after the `jumpSeen`
  statement — `olderDeferBehindPage(olderJob)`: a load on the MAIN thread that is not an older page, P-28 ON, with
  `olderPostsPending > 0`, runs again from a post queued BEHIND the page's pushes and its marker (`olderPostBehind(() =>
  loadMessages())`) and returns now. Counted before the test: either the page's check saw this load (it drops, nothing is
  queued) or the page pushed first (its gate release preceded this load's gate entry, so its increment is visible).
- `pushPendingJump()` on the main thread while `olderPostsPending > 0` posts itself behind the page the same way (the row
  the jump names may be among the page's queued rows): the quote jump (a widening load's jump) lands after them.
- A load on a pool thread, an older page itself, and P-28 OFF are unchanged: a pool thread's own pushes are posted in
  its program order, behind the earlier posts of the same queue.
The two orders (the page's pushes wholly before the other load's, or the page drops) now hold for what the shell RECEIVES.
