## What changed and why
- **Why.** The walk (`scripts/device/adb-walk.ps1`) must run its steps under a known switch state (P38–P41) without a tap on the Developer screen (the walk types no text, #1522) and without a new bridge verb or push (frozen). Options A, C, D of #1569 are not taken (`docs/review-brief-perfb1toggle.md` § 1).
- **The input.** ONE string extra `perfb1flags` (`PerfB1ExtraRules.ExtraName`, `Spixi/Utils/PerfB1ExtraRules.cs:14`) on the launch intent of the launcher activity (`MainLauncher = true`, `LaunchMode.SingleInstance`, `MainActivity.cs:51`, `:54`; legacy, `:27`, `:30` at `0e85a4b8`; the launcher is exported). Two call sites, both inside `#if SPIXI_DEV_COEXIST`: `OnCreate`, after `handleNotificationIntent(Intent)` and only when `bundle == null` (`:502-508`, the guard `:504`); and `OnNewIntent` (`:771`), after the existing `fa` call (`:781-784`). The reader is `:787-813`.
- **One-shot (the guard).** Android hands the SAME launch intent again to a re-created activity (a config change outside the handled list, a restore after a background kill) and to a launch from Recents. Without a guard the old four values would be stored again with no sender, also after Developer mode was left and turned on again, and over a later `ixian:devflash:` choice. Now `OnCreate` reads only on a fresh creation (`bundle == null`, `:504`), and the reader refuses an intent with `ActivityFlags.LaunchedFromHistory` (`:799-802`). `OnNewIntent` never replays: the file has no `SetIntent`.
- **The grammar (CANON).** Exactly `warmidle=<0|1>,sparerearm=<0|1>,sparekeep=<0|1>,noemptydetail=<0|1>`: 51 characters, all four names in this order, 16 legal values. `PerfB1ExtraRules.parse` (`PerfB1ExtraRules.cs:20-78`): a length check (`:32`) and an ordinal compare per position (`:38-76`), no `Regex`; names from `PerfB1Rules.DevSwitchNames` (`PerfB1Rules.cs:25`). Anything else refuses the WHOLE value: a refused value never stores a part. The file is wholly inside `#if SPIXI_DEV_COEXIST` (`:8`, `:81`).
- **The store.** `SpixiFlags.storePerfB1Extra` (`SpixiFlags.cs:191-212`, inside `#if`, `:185`, `:213`) reads "devMode" at that moment (`:195`), asks the rule (`:196`); off or refused → nothing stored, nothing logged (`:197-200`). On and CANON → four separate `Preferences.Default.Set` through `PerfB1DevKeys` (`:201-204`; the keys of #1560, `:35`; NO new key) and ONE fixed line `[FLAGS] perfb1 extra stored` (`:205`, `PerfB1ExtraRules.cs:17`). The catch stores no more and logs nothing (`:208-211`). **Not atomic:** the writes are four steps, then the line; a throw or a process kill between two writes can leave a part (only legal 0 / 1 values of the four keys) and no stored line; the walk's read-back catches it (csh `store_with_a_throw_at_the_third_write_logs_nothing`).
- **When it acts, and when it runs.** At the NEXT start: `SpixiFlags.init()` runs once in the `App()` constructor (`App.xaml.cs:248`); `init` (`SpixiFlags.cs:117`) and `leaveDevMode` (`:112`) are unchanged; no flag of the running process changes. Leaving Developer mode still removes the four keys and turns the opt-in off (`HomePage.xaml.cs:1862-1866`). The store also runs before login and under the app lock (the read is in `OnCreate`; no lock check): inside the three limits; it touches only the four preferences.
- **The worst effect, plainly.** While Developer mode is on, any app on that phone (or adb, or a shortcut) can send the extra to the DEVELOPER build and so set the four speed switches of batch 1a for the next start. Three choose between the new path and the old path of P38 / P39 / P41; the fourth turns the opt-in `SpareKeepShortSleep` (P40) on or off, and P40's own limits still hold (Android, app lock off, 3 minutes, unproven = dropped). It stops there: no other preference, no flag of another batch, no file, no verb, no navigation, no data out. Each such intent also brings the activity to the front, as any launch intent does (legacy). A store build has no reader; the developer build with Developer mode off stores nothing.
- **The `fa` path and the order.** `handleNotificationIntent` (`:823`) is byte-identical to the base. `OnNewIntent` runs on the main thread, where `MainThread.BeginInvokeOnMainThread` runs inline (the tree's own docblock, `:586-589`), so on BOTH paths the legacy `fa` read of `intent.Extras` (`:825-827`, no try / catch) runs BEFORE the new read. An intent with both extras: both act on their own.
- **Log lines: +1** in the APP's log: `[FLAGS] perfb1 extra stored`, fixed words; no value, length or name from the extra. The state line `[FLAGS] warmidle= …` (`SpixiFlags.cs:182`) is unchanged. A non-string extra under the name gives null → the app does nothing and logs nothing; Android's own Bundle code may write a type warning to logcat (the key and the type, never the value): from reading, unproven here. A huge string is refused at the length check.
- **The walk side (scripts only; Damir's PC and the TEST phone; #1522 holds).** `-Flags <CANON>` is checked anchored and case-sensitive before any adb command (`adb-walk.ps1:2398`; `-Calibrate` refused, `:2396`; the three assignments sit in the `else` of that check, so an unchecked text is never adopted whatever `Exit-Usage` does). ONE new allowlist shape `am start -n <component> --es perfb1flags <CANON regex>\z` (`:463`); two new count polls (`:146-147`); ONE new alternative in the phone-side filter `$script:LogRe` (`:150`), the exact state line only. `Invoke-FlagsSetup` (`:1334`): `am force-stop` → `logcat -c` → the start with the extra (always cold) → stored-line poll (30 s) → a 2 s settle (`$script:FlagsStoreSettleMs`, `:156`; the app writes its preferences asynchronously) → `am force-stop` → `logcat -c` → `am start -W` → state-line poll (45 s) → settle → ONE pid-filtered pull `android-walk-flags-00.txt` → the state is re-built from four digits (`Get-FlagStates`, `:1274`) and compared. **The count polls are not pid-scoped and only end a wait; the proof is the pid-filtered read-back.** An am error or the note "intent not delivered" stops at once (`start-failed`, `:1344-1345`).
- **The pid guard.** In a `-Flags` run every number comes from an app process whose own state line was read: the proven pid is kept (`$script:FlagsPid`, `:1364`); a coldstart rep must show the state line in its own log (none = stop `no-state-line`, `Update-FlagsLogged`, `:1292-1323`); every other log pull and the memory phases need the proven pid (`Assert-FlagsPid`, `:1261`; memory `:1721`); a restart inside the run (`Reset-AppToChats`, `:1210`) stops it. Six stop codes (`$script:FlagsStopText`, `:159-166`): start-failed, not-stored, no-state-line, pull-failed, state-differs, unproven-process; each ends the run (exit 1) and no number row is written. A stopped run has no `summary.md` (the driver does not call the parser); `run.json` holds `flags` (`:1141-1146`).
- **The parser** (`adb-walk-parse.ps1`, `Get-FlagsStatus` `:891`, `$withheld` `:1074-1075`) withholds every number in an asked run when: the state is not proven or differs (exit 2 / 4, `:1203-1216`); a coldstart rep log has no state line (a coldstart rep with status ok whose `log` key is missing or is not its own derived name counts the same); a named rep log is unreadable or over 4 MiB; `flags.stop` is any non-null value (an unknown code prints fixed words, never the raw value). Without `-Flags` it reads all rep logs; more than one state prints the fixed line "Switch state: mixed (…)" (a warning; exit code and `summary.csv` do not change); `summary.csv` of an old run folder is byte-identical. **After a `-Flags` run the four developer preferences stay changed on the phone.**

## How to switch it off
This is dev-build tooling, not a user-facing change, so there is no runtime switch (#1312 / #1478). Its switches: Developer mode off (nothing is stored; leaving it also removes the four keys), or build without the `SPIXI_DEV_COEXIST` symbol (a store build has none of it).
