## What changed and why
- **Why.** The adb walk needs a chat full of image tiles to scroll and to open (a 6-photo album included). The old seed made 50 text contacts only.
- **What it makes.** Seed index 50, 51, 52 (`addressFor(i)` like the fifty; nicks "Seed 51 Petra Hočevar" … "Seed 53 Alenka Bregar", `SDevSeedPlan.imageNick`, `:146`; names `:112`): 70 messages, 46 photos, made in code as 8-bit palette PNGs with stored deflate blocks (`SDevSeedPlan.png`, `:423`; no encoder, no bundled picture; 480–1280 px an edge, about 1 byte a pixel). Seed 52 holds ONE received album of 6 (`SPhotoGroups.setMany`, `SDevSeed.cs:311`). The times are FIXED, not relative to now: `SDevSeedPlan.ImageAnchor = 1767268800` (2026-01-01 12:00 UTC, `SDevSeedPlan.cs:99`); the newest message of Seed 51 is at the anchor, Seed 52 one hour and Seed 53 two hours earlier. The same on every seed run, and older than every Seed 01–50 message of any run made after 2026-01-31, so the first rows of the chats list stay as they were. Fixed times, 2026-01-01 12:00 UTC for the newest; the day label can differ by a day in far time zones (cosmetic).
- **The rows are the app's own shapes.** A received photo: the `uid:name:size` header row plus the fields a completed transfer leaves (`transferId`, `filePath`, `fileSize`, `completed`; `SDevSeed.cs:294-300`; `completed` is set BEFORE `filePath`, the order `TransferManager.completeFileTransfer` uses, because Core's writer thread reads the row without a lock, #46 r1 B-5), the file in the downloads folder. A sent photo: the `uid:name` row with its durable copy `Sent/<uid>.png`. The chat page finds the files through `SharedItems.localPathOf` and makes its thumbnails itself: nothing new on that path.
- **Who names the files.** C# only, from the seed index: a received leaf `devseed-NN-JJJ.png` (`SDevSeedPlan.photoName`, `SDevSeedPlan.cs:260`), a sent leaf `<32 hex of SHA-256>.png` (`transferUid`, `:248`; `localLeaf`, `:267`). The temp leaf is `SDevSeedPlan.tmpLeaf(i, j)` (`:278`) = `pending-<16 hex>-0.src`, the app's own pending-photo name shape, in the app's own `Sent` folder for BOTH directions (never in the downloads folder, where a peer names files). Roots: `Config.spixiUserFolder` + `Sent` and `TransferManager.downloadsPath` (`SDevSeed.cs:231-232`). Before a write, fail closed: a sent leaf must equal `PhotoRules.sentFileName(uid, ".png")`, a received path must pass `TransferManager.isInsideDownloadsRoot` (`:271-272`, else counted refused).
- **A re-seed is a top-up, decided by CONTENT.** `SDevSeedPlan.fileState` (`:299`) answers `absent` / `ours` / `foreign`: ours = the same length AND the same SHA-256 as the PNG the plan builds. Ours is kept; a foreign file is never overwritten, never adopted and never deleted (counted as refused). Absent: written to the temp leaf in `Sent`, then `File.Move(tmp, path)` without overwrite (`SDevSeed.cs:356-360`; it throws if a file appeared meanwhile, and the caller counts that). A temp left by a kill is removed by the app's existing startup sweep of pending photos and by the account wipe; unseed deletes it by its exact name only (`deleteOwnTmp` `:371`, `mayDeleteTmp` `SDevSeedPlan.cs:336`). Core refuses a message id it holds, so nothing doubles.
- **Unseed.** The one removal loop now walks 53 indexes (`:456`). One older statement moved inside `unseed()`: `UIHelpers.shouldRefreshContacts = true;` now stands after the `unseedImageChats()` line (`:471-473`), so the list refresh is asked after the image files are gone (#46 r4 R4-2; no Seed 01–50 id, count, time or removal changes). Then `unseedImageChats` (`:387`) clears the photo-group entries (`:403`) and deletes each file C# wrote, by the same built names, ONLY with proof by content: `SDevSeedPlan.mayDelete(state)` (`:329`) is true for `ours` only (`SDevSeed.cs:425-427`); a foreign file with our name is counted as refused and stays. Our own temp leaf goes by its exact name (`:419`). A contact whose removal was refused keeps its files (`:398-401`). The one new file read is `File.ReadAllBytes(path)` of a file of our exact length, for hashing only (`:335`).
- **No network, no shell change, no new store key, no switch.** The status sentences (`setDevSeed` push) gain a fixed sentence with counts.
- **The four new log lines** (`SDevSeed.cs:306`, `:320`, `:438`, `:446`): `[DEVSEED] image message <i>:<j> skipped (<Type>)` · `image chats stopped (<Type>)` · `image file <i>:<j> not removed (<Type>)` · `image chats removal stopped (<Type>)`: fixed words, seed index and message index, exception TYPE names only.
- **Three older lines made type-only (#46 r1 S-1).** `[DEVSEED] message <i>:<j> skipped: <Type>` (`SDevSeed.cs:193`), `[DEVSEED] remove <i> failed: <Type>` (`:468`), and in `SettingsPage.handleDevSeedVerb` the pushed `Seed failed: <Type>` / `Remove failed: <Type>` and `Logging.error("[DEVSEED] " + <Type>)` (`SettingsPage.xaml.cs:179`). Why: unseed now reaches `FriendList.removeFriend`, which deletes files and a directory, and a .NET IO exception message carries the full path with the OS user name and the address. Pin `e-image-seed` row 5 holds that no `[DEVSEED]` line carries `.Message`, `.ToString()` or a bare exception.
- **Debuggable dev builds.** Dev builds are debuggable (the walk handoff saw `pkgFlags` DEBUGGABLE on the Release dev build), so `adb shell run-as` can write these two folders directly. That holder already has the app's trust level; the seed adds no way in.

## NOT proven
- ⚠ C# UNCOMPILED: `SDevSeed.cs` needs Core and MAUI; only the pure half runs in csh. No dev build has seeded the image chats yet; whether the chat page shows the tiles and the album as built is for the device sitting.
- The verbs have no dev-mode test (inherited from Session I, P21 row): safe only because the code does not exist in a store build.
- Disk: 46 files of up to about 1.2 MB in the Sent folder and the downloads folder of a dev build (not measured).
- CLOSED in this batch (#46 r1 B-2): the old residual "a user file with the same built name AND the same length would be deleted" no longer holds. Keep and delete need proof by content (same length AND same SHA-256); a foreign file is never overwritten, adopted or deleted. Still open: a user file whose bytes equal our deterministic PNG exactly under a built name would count as ours; that is the seed's own file by definition.

## How to switch it off
There is none: use a build without `SpixiDevCoexist` (every store build). In a dev build `ixian:devunseed` removes the contacts, their album entries and the files.
