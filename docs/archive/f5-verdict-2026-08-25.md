## 0. ★★ THE HEADLINE: the notification lane was aimed at the wrong hook

**#493's premise was wrong, and the evidence is unambiguous.**

The registration works, and early:

```
13:34:42.367  [NOTIFDIAG] OneSignal handlers registered in the Application (#493)
```

— before `MainActivity created`. And `Cannot clear notifications` is **gone** from the log,
so that half of the row landed.

But **no** `raw push suppressed` and **no** `cold push posted as a Spixi row` appears in
3,422 lines. The handler registers and never fires. The screenshots agree: three or four
SEPARATE Spixi rows with Android bundling them, where our poster keys **one id per chat**
and can only ever produce one row that updates.

★ **And our own manifest has said so since #334:**

```xml
<!-- accent for OneSignal SDK-rendered notifications (background…) -->
<meta-data android:name="com.onesignal.NotificationAccentColor.DEFAULT" …/>
```

There is a separate path where the OneSignal SDK renders the notification **itself, in
native code, for background delivery** — we style it with its own accent and its own small
icon and have done for months. `WillDisplay` is a **FOREGROUND lifecycle listener**. It was
never going to fire for a killed app, at any registration time.

| Row | Verdict |
|---|---|
| 2.4 master OFF still notifies | ✗ — same cause |
| 2.5 ungrouped rows across two chats | ✗ — same cause |
| 2.6 muted 1:1 still notifies | ✗ — same cause |
| **2.1 four messages → one row** | ⚠ **FALSE PASS.** That "4" badge is Samsung bundling four separate notifications, not our single updating row |

**THE FIX, and it is the same shape on both platforms:** a **`NotificationServiceExtension`**
— `<meta-data android:name="com.onesignal.NotificationServiceExtension">` implementing
`IRemoteNotificationReceivedHandler`, which OneSignal invokes for EVERY notification
including background, and where a notification can be suppressed or rewritten before
display. **We have none, on either platform.** #487 said iOS needed an NSE and implied
Android did not; the truth is Android needs one too and the platforms are closer than that
row claimed. Own batch, own audit.

## 4. ★ The desktop lock model is wrong, and Damir asked the right question

He asked whether Windows needs a different grace — *"5 minutes?"*. **The grace period is the
wrong dial, because the SIGNAL is wrong.** On a phone, "backgrounded" means the phone left
the user's hand. On a desktop it means they clicked another window — which is exactly how
he got locked out mid-sentence while typing to Claude.

**Proposed, for the next batch:** no lock on deactivate at all · lock on **system lock or
sleep**, which is the real "I walked away" event and is free to detect · lock after **~10
minutes of input idle**, configurable. One dial a user can predict, and it never fires while
they are using the machine. ⚠ Security-gate row, and it needs the escape hatch too (W-4.6).

## 5. What this pass taught

* ★ **A fix can be correct, verified, pinned, mutation-tested — and aimed at the wrong
  layer.** Every gate in this batch was green. The device said the lane does nothing,
  because `WillDisplay` is a foreground listener and always was.
* ★ **The answer was in our own repo, in a comment we wrote.** #334 styled the
  "SDK-rendered background" path by name. Nobody re-read it while writing #483.
* ★ **A pass can be a FALSE pass.** 2.1 read as a win and was the platform's bundler.
  Reading the screenshot rather than the tick is what caught it.
* ★ **Nine batches without a device is the defect.** N65 was solvable the day #385 shipped.
* ★ **"Never build past a missing repro" has a third half: don't build past a missing
  MECHANISM.** #501 was caught before shipping; #493 was not.
