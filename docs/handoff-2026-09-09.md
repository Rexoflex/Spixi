## ★ The two answers

### 1 · The memory kill is NOT a page leak (#830, AND-40)

22 minutes of real use on Damir's Motorola, one process:

* `memHeld` **pinned at 3** across **74 page loads / 71 releases**. Never 4.
* PSS reads as growth (261 → 342 → 362 MB) but **swap falls 140 → 46 → 43** —
  `PSS + SWAP` is **402 / 387 / 405 MB**. Flat.
* No `lowmemorykiller`. The only process death in 24 297 lines is his own swipe.

⚠ **The defect is not closed — it did not reproduce.** A hypothesis was eliminated.
The floor is the story: **Code 67 MB PSS / 206 MB RSS** plus a **94 MB native heap**,
Java heap 72 KB. 511 MB over a ~400 MB floor is a **transient spike**, not accumulation,
so the next run should chase native/graphics — image decode, camera/QR, the call stage —
and needs a run that actually kills, with the streaming logcat kept alive across adb drops.

⚠ #824's promised cross-check does **not** hold as stated: `memHeld` and dumpsys
`WebViews:` diverged (3 vs 5 at peak) because disposal is synchronous and the native
object dies at GC. The usable form is *climbs and never returns*, not equality.

## The bridge, for whoever picks this up

`device_bash` runs on a Linux VM with the repo mounted. **No `dotnet`, no `adb`, no working
tree-sitter** — the C# cannot be compiled or syntax-checked here, and `cs-syntax-check` is
skipped every session. `smoke-test.mjs` in full exceeds the call timeout; individual gates
run fine in a harness **assembled from the suite's own header** (#828 — a harness you write
yourself is not verification). Plain `git status` strands `.git/index.lock`; use
`--no-optional-locks`. The mount cannot delete: move to `_to_delete/`, which is gitignored.
