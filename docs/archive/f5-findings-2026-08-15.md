### D-1. Avatars are missing after an account restore. **BE / Ixian-Core.** Medium.

Damir: *"the account backup file doesn't store the avatars, so it would be great if it

⚠ **Ask the BE engineer this first.** `LaunchRestorePage.xaml.cs:230` sets

### D-6. ★ ACCOUNT IS THE HIGHER TIER. The delete semantics are inverted today. **Damir, 2026-08-15.**

**Damir's ruling, verbatim in effect:** an ACCOUNT is the wallet PLUS the contacts. Deleting
the account is complete destruction — nothing remains, and only Restore or Create works
afterwards. "Delete wallet" is probably redundant and should likely go. The screens must SAY
this: **ACCOUNT = WALLET + CONTACTS.**

🟡 He is checking with the BE engineer whether anything depends on the two being separate.
**Nothing is built on this yet.**

**What the code does TODAY — the opposite way round.**

| Verb | What it destroys | Where |
|---|---|---|
| `ixian:deletea` "Delete account" | Avatars, account file, downloads, pending messages, chat history, friends. **The wallet SURVIVES** | `SettingsPage.wipeAccountData` |
| `ixian:delete` "Delete wallet" | The wallet file, `walletpass`, `onboardingComplete`, the databases, the node — **AND it calls the account wipe as well** | `SettingsPage.deleteWalletWork` |

So the LOWER-tier-sounding action is the total one, and the higher-tier-sounding action is
the partial one. That inversion is the root of the dead end found in batch #348 review:
after "Delete account" the user lands on the welcome screen, and Create refuses with *"An
account already exists on this device"* — because the wallet the action kept is still there.
The dead end was treated as a consequence to accept. **It is not. It is a symptom of the
semantics being backwards.**

**What Damir's model implies.**

1. **Delete account = the full teardown.** `ixian:deletea` should do what `deleteWalletWork`
   does today. Welcome then becomes a true state and Create works, which removes the dead
   end entirely rather than documenting it.
2. **Delete wallet probably disappears.** If an account IS the wallet plus the contacts,
   a wallet-only delete is not a user-meaningful action. Removing it also removes the
   `walletGone == false` error branch and the one route that stays put.
3. **The copy must state the scope BEFORE the destructive act**, on the danger row, in the
   confirm sheet, and on the delete-data screen. "Delete account" alone does not tell a user
   their money is included.

**The batch #348 W14 work stays valid either way.** The freeze fix, the removal of the
`onLoad()` re-read, the parked-document dispose, the one-shot latch and the `LaunchRestorePage`
guard are all about HOW the teardown runs, not about WHICH data it takes. If the account
route becomes the full teardown, it inherits all of it — and the `LaunchRestorePage` guard
becomes unnecessary rather than wrong, because a live wallet can no longer sit behind
onboarding.

**Effort: small in code, and it SIMPLIFIES.** One route instead of two, one confirm copy
set, fewer branches. The cost is the strings (8 locales, via `src/strings/en-us.json` and the
generator — never hand-edit the built locale files) and one careful F5 on a throwaway
account. ⚠ The one thing to confirm with the engineer first: does anything — key derivation,
a device pairing, an Ixian identity — need the wallet to outlive an account wipe?

### D-7. ★ The new Restore guard has no way forward. **OURS, from batch #348. Small.**

**Damir hit this immediately:** after a delete-account test he could not restore. Restore
says *"An account already exists on this device. Restart Spixi to continue with it."*, and so
does Create. From the welcome screen there was no door and no instruction.

**Cause — and it is ours.** Batch #348 added a `getWalletList().Count > 0` guard to
`LaunchRestorePage` (Damir's call: delete-account routes to welcome and keeps the wallet, so
Restore would otherwise have run over a live wallet). The guard is correct. **The COPY was
copied along with the logic**, and it does not fit the new caller:

- On `LaunchCreatePage` the message is fine — someone who hit Create by mistake is told the
  account they want is already here, so restart and use it.
- On `LaunchRestorePage` the user is deliberately restoring a DIFFERENT account. "Restart to

**Net effect of the batch on this state: one dangerous door became zero doors.** Before, the
user could restore (destroying the wallet silently). Now they can do neither, and are told
only to restart.

**The way out, for the record:** restart (the app boots back in, because delete-account
leaves `onboardingComplete` set) → Account → Delete wallet → then Create and Restore work.
No user would find that unaided.

**Fix options:**

| Option | What | Note |

| A | Make the message actionable — name the step: delete the existing account first, and where | Small. Strings only. Correct regardless of D-6 |
| B | Let **D-6** remove the need — if an account wipe always takes the wallet, no wallet can outlive it and the guard becomes dead code | Preferred, but blocked on the engineer |

🟡 Damir's call. Option A is safe to do now and is not wasted if D-6 lands — a clear message

2. **The native page transition itself**, which is the same lever as idea **I-1**

**First step: one `PerfTrace` reading on welcome → create**, the same way #345 was measured.

### D-9. ★★ DELETE-ACCOUNT LEAVES THE APP UNBOOTABLE. Black screen on the next start. **Highest.**

**Damir, on device, 2026-08-15:** after a delete-account he restarted and got a black screen.
The app never reached Spixi at all. The Visual Studio debugger broke on an unhandled
exception with this frame in the Output pane:

```
at SPIXI.HomePage.<.ctor>b__34_2()
08-15 12:16:16.4505|info|2: Windows OnWindowCreated - ensuring Node is running
08-15 12:16:16.4507|info|2: EnsureNodeRunning: Node is already running
```

**Why startup goes there at all.** Delete-account wipes the account but KEEPS the wallet, so
`App.xaml.cs:141` `Node.checkForExistingWallet()` returns **true**, the wallet decrypts
(`:151-155`), the lock is off, and startup takes `:175`:

```csharp
MainPage = new NavigationPage(HomePage.Instance());
```

It goes straight to HomePage — a HomePage whose account file, friends, avatars, downloads and
message history were all deleted.

**The strongest candidate for the throw** (ordinals are compiler-assigned, so this is
inference, not proof) is the constructor's async start lambda,
`Spixi/Pages/Home/HomePage.xaml.cs:234-257`:

```csharp
Task.Run(async () => {
    try { if (!Node.start()) { await displaySpixiAlert("Fatal exception", ...); return; } ... }
    catch (IOException e)  { ... await displaySpixiAlert(...); }
    catch (Exception e)    { ... await displaySpixiAlert(...); }
});
```

The `catch (Exception)` is total, so the ONLY way an exception escapes this lambda is if
**`displaySpixiAlert` itself throws inside the catch**. That is plausible at this moment:
the alert is hosted on `Application.Current.MainPage` (`SpixiContentPage.cs:1820`), and this
runs while `MainPage` is still being assigned during `InitializeComponent` — the debugger's
own stack frame says `Spixi.WinUI.App.InitializeComponent`. On WinUI a `ContentDialog` with
no usable `XamlRoot` throws. The audit note at `SingleChatPage.xaml.cs:628-631` already
records the sibling of this problem: *"an alert on an unattached page is silently lost"*.

**So there are two defects stacked, and both should be fixed:**

| # | Defect | Fix |
|---|---|---|
| 1 | `Node.start()` fails after an account wipe, because the account data it needs is gone | ★ **D-6 removes this entirely** — if delete-account also takes the wallet, `checkForExistingWallet()` returns false and startup goes to LaunchPage, which is the correct screen for "no account" |
| 2 | The failure is INVISIBLE — the error path throws while reporting the error, so the user gets a black screen instead of "Fatal exception" | The start lambda must not depend on an alert being presentable. Log first, then attempt the alert inside its own try/catch, and fall back to routing to LaunchPage rather than dying |

**#2 matters even after D-6.** Any future startup failure will produce the same black screen,
because the reporting path is the thing that breaks. A crash that cannot announce itself is
the worst possible failure mode, and it is one `try` away from being fixed.

**How Damir got out** (worth recording — no user would find it): move `Documents\Spixi`
aside so `checkForExistingWallet()` returns false, launch, then Restore from a backup file.

⚠ **This is the strongest possible argument for D-6.** The two-tier model does not merely
produce a confusing welcome screen — it produces a state the app cannot start from. Batch
#348 did not create it (the wipe set is unchanged), but #348 made it immediately reachable,
because it routes the user to welcome and the alert there tells them to restart.

**Effort: small** for #2. #1 is D-6.

#### 🟡 RESIDUAL, logged and NOT fixed in #348 — the half-committed tip window

Review r2, finding 2b. The tip case is now inside one `try`/`catch`. The `catch` always
answers `sendTipResult(false, …)`, thus the sheet always shows **"not sent"**. But three
operations occur in sequence after the balance check
(`SingleChatPage.xaml.cs:1348-1356`):

1. `friend.addReaction(...)` — writes the tip pill into the LOCAL message store
2. `StreamProcessor.sendReaction(...)` — tells the peer
3. `IxianHandler.addTransaction(...)` — broadcasts the money

If step 2 or step 3 throws, step 1 has already committed. The user then sees a sheet that
says the tip failed, and a tip pill on the message that says it did not. The money state is
unknown: `addTransaction` is the last operation, so a throw inside it can leave the
transaction either broadcast or not.

**Why it stays open.** Three reasons, all of them the project rules:

- An honest answer needs a THIRD result state ("we are not sure"), and therefore a new
  string in 13 locale files. This is the same block that holds **D-12**.
- To roll step 1 back, we must remove a reaction. `Friend.addReaction` is Ixian-Core and
  the repository holds no evidence of a remove counterpart. **#215: zero C# without
  evidence.** Ask the BE engineer.
- The window is narrow and it is not new money risk: before #348 the same throw escaped
  into `onNavigating` and destroyed the conversation document. The `catch` is still a
  large improvement over that.

**Introduced-vs-inherited: INHERITED.** The three-step sequence and its order are legacy
(`SingleChatPage` predates the redesign). #348 added the `catch` and the answer, not the
window. → The BE engineer sees this one.

**Next session:** put the remove-reaction question to the BE engineer together with D-12.
One answer unblocks both.

## PART 2 — IDEAS

### I-1. Slide and fade the chat in from the right, and back out on swipe-back. Worth doing.

This is the honest version of what **#343** tried and got wrong. That batch chased perceived
latency with a spinner delay and a log fade, and on device it made chat entry WORSE and was
reverted the same night.

A DIRECTIONAL transition is a different mechanism. It gives the eye something to track
during a wait that already exists, instead of trying to hide the wait. That is the one
motion trick that reliably buys perceived time.

**Three constraints that decide the build:**

1. ★ The chat is its own native WebView (**#221 isolation**). The transition therefore has
   to be NATIVE-side — a CSS transition inside the shell cannot move a sibling WebView, and
   composing them into one WebView to make it possible is exactly what #220 rejected.
2. **Measure on the A52 before judging it.** #343 is the precedent for why. A transition
   that adds real milliseconds to a slow device does not buy perceived time, it spends it.
3. ★ **MOBILE ONLY** (Damir, 2026-08-15). Build the transition on the mobile navigation
   path only. On desktop the chat is not a pushed page: it is a pinned pane in a grid
   column, and both panes stay alive together. Nothing comes in from off the screen there —
   only the CONTENT of the pane changes. A slide from the right therefore has no meaning on
   desktop, and a transition that moves the pane would fight the #221 per-pane WebView
   layout, which is the one place where the two WebViews are on the screen at the same time.
   Gate the transition the same way A9 gates the rail pane: on the PLATFORM
   (`DeviceInfo.Platform == WinUI || MacCatalyst` is desktop), not on the window width and
   not on `DeviceInfo.Idiom`. Idiom is posture-dependent and gave the wrong answer in A9.

Also note the existing floor: ~185 ms of JS compile and execute survives even after #345,
