## D1 — REPLY TO A MESSAGE. ★ DESIGN LOCKED, Damir 2026-08-15.

**Verdict CHANGED from the "BE-blocked" line in `handoff-341-next.md`.** That verdict meant
Ixian-Core, and the BE engineer is right that Ixian-Core is not needed.

### The locked design

- **No protocol change.** The reference rides in the message body as a marker carrying the
  referenced message's ID.
- **★ Reference by ID. Resolve the quote LOCALLY. Never send the quoted text.** If the text
  rode along, a sender could render words the other person never wrote, attributed to them.
  That is a spoofing surface created purely by the shortcut, and it is very hard to walk
  back once shipped.
- **Tapping the quote in the bubble jumps to the referenced message.**
- Referenced message missing, deleted, or outside the loaded window → a neutral
  "Original message" placeholder. **Never sender-supplied text.**

### Why it works — evidence, not opinion

1. **Message ids already cross the wire and resolve on the OTHER device.** Reactions are the
   working precedent: the shell sends `ixian:contextAction:like:<hex id>`
   (`SingleChatPage.xaml.cs:264`) and the counterpart applies it to their own copy.
2. **C# already resolves a message by hex id against the local store** —
   `SingleChatPage.xaml.cs:958`, `friend.getMessages(channel).Find(x => x.id.SequenceEqual(Crypto.stringToHash(msg_id)))`.
   That is the lookup a reply needs, and it exists.

### The four pieces

| # | Piece | State |
|---|---|---|
| 1 | Sender shell tells C# "send this text, replying to id X" | Small C#, new or extended verb in `SingleChatPage` |
| 2 | C# writes the marker into the outgoing body | Small C#. **Decided: body marker, no protocol change** |
| 3 | Recipient C# passes the parent id up as a 13th push argument | Small C#, additive — same shape as the `getAppInfo` extension in #214 |
| 4 | Recipient shell resolves the id and renders the quote | **Already built**, gated on `bridge.cap('reply')`; the chat shell needs a `setCaps` handler |

### Verify BEFORE building (#215)

**Two-device test: is a message's id the same on both devices?** Reactions strongly imply
yes, but the whole design rests on it. Five minutes beats an assumption.

### Consequences to handle in the build

- The SENDER's own copy carries the marker too, so the sender's shell must strip it when
  rendering. Neither side may show the raw marker.
- A client that does not parse the marker shows it as raw text — legacy Spixi, other Ixian
  clients, older versions. **Damir accepted this** as the price of no protocol change.
- The jump target may not be in the loaded window (25 messages). Reuse the mention-jump
  machinery; if the message cannot be reached, do not fake it.
