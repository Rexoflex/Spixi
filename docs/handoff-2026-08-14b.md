## The headline: chat open is measured 56% faster

Galaxy A52 5G, Debug build, warm open, `PerfTrace`:

| Mark | Before (#341) | After (#345) |
|---|---|---|
| `generatePage(chat.html)` | 172 ms | **37-51 ms** |
| `loadPage returned` | +191 ms | +55-62 ms |
| `shell onLoad` | +472 ms | **+210-214 ms** |
| message push, 2 msgs | 24 ms | 3-12 ms |
| **`loadMessages done`** | **+498 ms** | **+215-227 ms** |

Damir on device: *"it feels snappier and better."*

**How.** Every shell inlined the SAME ~1.6 MB — the component bundle, the strings
dictionary, the icon sprite and the base/token/pattern CSS. Across 22 shells that is
~35 MB of identical bytes, and Android re-read, re-localized and re-base64-encoded all
of it on EVERY navigation. Those six files are now emitted ONCE beside the shells.
`chat.html` 2019 KB → 370 KB · `index.html` 1625 KB → 309 KB · `lock.html` 1347 KB →
31 KB.

**Side effect worth knowing for the lead-dev conversation:** the repo went from
**1,052,380 lines to 620,416** — 432,000 lines gone, because the built HTML was mostly
duplicated bundle. The "half a million lines of unreviewable generated HTML" is now
about 71,000, and it dropped as a consequence of a measured performance fix.

## What remains, and it is a floor not a bug

Of the ~220 ms that is left, about **155 ms is the browser parsing the HTML and
compiling and executing the JavaScript**. DevTools measured the same thing
independently at 185 ms. The same code still runs; #345 only stopped re-delivering it.

To go below that floor you need one of:

1. **Per-shell bundle splitting** — ship each screen only the exports it uses. The
   bundle has 252; `lock.html` needs about ten. This cuts EXECUTION, not just bytes,
   and it is the biggest remaining lever.
2. **A warm WebView.** `AND-10` already asks whether the #177/#225 warm-page machinery
   runs on Android. A warm page removes the whole cost, not part of it. ⚠ Damir
   REJECTED parking chat WebViews (memory, and multi-window later) — do not re-propose
   that specific shape without new evidence.
3. **Batching the message push** (#298). Measured at ~12 ms per message, so this
   matters on busy chats, not on the 2-message test chat.

**Before any of that: build RELEASE and re-measure.** Everything above is a Debug build
on a worn 2021 mid-ranger. Debug on Android means no AOT and no trimming. Release on
decent hardware could plausibly halve these numbers again, and it would change which
lever is worth pulling.

## Open, with evidence

### The "connecting" banner is stuck on Android — REAL BUG, not cosmetic only

- Android shows "connecting" permanently. **Windows does not. Legacy Spixi does not.**
- **The wallet balance loads**, so the DLT genuinely IS connected. The banner is lying.
- logcat shows the normal cause of a flicker: `Network client connected to
  167.235.2.158:10237` then `Sending bye … 'Disconnected for shuffling purposes.'`
  Ixian rotates connections, so the client count hits zero briefly.
- The C# state machine (`HomePage.xaml.cs:2259-2285`) SHOULD self-clear: two
  consecutive zero-client ticks show it, the next connected tick clears it via
  `if (warningDisplayed) showWarning("")`. One link in that chain is not firing on
  Android. **Reading the code did not identify which.**
- **Next step: instrument it.** Three lines in that branch logging the client count,
  what it pushes and the `warningDisplayed` flag. `PerfTrace` is still in the build.
  One capture names the broken link. Do NOT fix it before that.

### Related, and already in better shape than legacy

On legacy, "update available" and "connecting" shared one vehicle. On new Spixi they are
already separated (`home.html:2798`, the #59/M16 decision): connectivity becomes a quiet
topbar title state, everything else gets the actionable banner. Worth seeing the update
message render once to confirm, but the mechanism is right.

## Lessons this batch paid for, twice

1. **#343 shipped three changes aimed at a cause inferred from reading code.** On device
   they made chat entry WORSE and were reverted the same night. The measurement that
   followed showed the real cost was somewhere none of them touched.
2. **A guard that fires is doing its job.** The #345 boot guard showed a red panel on
   Windows — a false positive on `empty_detail.html`, the one shell that never carried
   the bundle. It was fixed in minutes precisely because it failed loudly instead of
   showing a blank pane.
3. **Read the URL bar.** The whole diagnosis started from noticing
   `data:text/html;charset=utf-8;base64,` in DevTools on the device.
