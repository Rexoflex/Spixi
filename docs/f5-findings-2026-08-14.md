## D1 — REPLY TO A MESSAGE. Verdict CHANGED, 2026-08-15.

The BE engineer says reply needs no Ixian-Core change: it references a message already in
the chat, skins it, and mentions the user. **He is right, and the earlier "BE-blocked"
verdict in `handoff-341-next.md` was too conservative.** Evidence, not opinion:

1. **Message ids already cross the wire and resolve on the OTHER device.** Reactions are
   the working precedent — the shell sends `ixian:contextAction:like:<hex id>`
   (`SingleChatPage.xaml.cs:264`), and the counterpart applies it to their own copy of
   that message. Damir F5-confirmed reactions round-tripping. So an id is a valid
   cross-device reference.
2. **C# already resolves a message by hex id against the local store.**
   `SingleChatPage.xaml.cs:958` — `friend.getMessages(channel).Find(x => x.id.SequenceEqual(Crypto.stringToHash(msg_id)))`.
   That is exactly the lookup a reply needs, and it already exists.

### ★ The design detail that matters

**Reference by ID and resolve LOCALLY. Never embed the quoted TEXT in the sent message.**

Embedding the excerpt is the obvious shortcut and it is the wrong one:

- It is **attacker-controlled**. A sender could quote words the other person never wrote,
  and the app would render them as that person's words. That is a spoofing surface on a
  messaging app, and it is created entirely by the shortcut.
- Any client that does not parse the marker shows it as **raw text** in the message body.

Resolving by id has neither problem, and when the quoted message is not in the loaded
window the honest fallback is a neutral "Original message" placeholder — never
sender-supplied text.

### What still has to be decided, and verified first (#215)

- **How the id travels.** Reactions have their own message type with a target id; a text
  reply has no such field. Either a marker in the body (pragmatic, but see the raw-text
  caveat) or a new typed carrier. This is the one real question for the BE engineer.
- **Two-device test BEFORE building:** send a message, reply to it, and confirm the
  recipient resolves the referenced id to the right message. The whole design rests on
  that, and it is cheap to check.
- **The mention half** is already built (#212/C13) and should be reused for the notify.

The FE half is complete and gated on `bridge.cap('reply')`, which is false today because
the chat shell has no `setCaps` handler. Adding one is small.
