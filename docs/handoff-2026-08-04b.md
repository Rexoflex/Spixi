### 1. Scan DECODE — r3 scanned (slowly), r4 recognizes nothing ★ start here

Timeline is the evidence: with the r3 accidental layout (feed 262×349 ≈ the stream's 3:4) QR
decode WORKED, just slow. r4's only change was layout (full-bleed 393×737 feed + `object-fit:
cover`) — and decode went to zero. **Prime suspect: html5-qrcode's decode-region math.** It maps
CLIENT dimensions onto intrinsic frames assuming its OWN default styling (video width = container,
height = auto → aspect preserved, no crop). Full-bleed + cover breaks that assumption — the
region sampler plausibly reads a wrong/cropped sub-region now.

**#215 gate: verify in the vendored lib first** (`Spixi/Resources/Raw/html/js/html5-qrcode.min.js`
— search the region/bounds code, e.g. `getShadedRegionBounds`, `qrRegion`, what feeds the decode
canvas dimensions). Then fix candidates, ranked:
 (a) **Aspect-locked feed** — size the feed to the stream's aspect (3:4), centered in the camera
     bed with the bed's dark ground as letterbox — the classic scanner look, keeps the lib's
     assumed geometry exactly, pure CSS/JS;
 (b) explicit `qrbox` in the start config (decouples region from client size);
 (c) region-math override — last resort, touches vendored code.
Also re-judge speed ONLY after decode works again (r3's "slow" was likely aim-vs-cutout mismatch,
now fixed); if still slow, MEASURE fps (10 = legacy parity) and whether A8's min×2 auto-zoom
blurs close-range codes before touching either.
