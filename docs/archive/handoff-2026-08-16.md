## What landed today

**Search (the real bug).** A query is now scoped to ONE VISIT to its surface: it
survives scrolling, blur and drilling into a result, and dies when the surface is left
(tab switch, takeover, Account pane). Deliberately NOT clear-on-blur — blur fires when
you tap a result, so it would discard the query of a user acting on it. While a filter
is live the field wears the action outline, so an on filter is legible at rest.
Implemented once in `search-field.js` (`resetSearchFields({ keepWithin })` + a
self-pruning registry) so Chats/Wallet/Apps inherit it; the takeover-scoped fields
(contacts, wallet-send/receive, chat-info, settings-app) die with their DOM already and
just gain the affordance. The chip filter and `leaveRequestsFilterIfEmpty` are untouched.

**Apps perf — the real causes.** Last night's FE row-reconcile was correct but was not
the bottleneck (Damir: "no change"). Fixed at source: `sendUiCommand` was base64ing an
already-base64 icon (240 KB → 320 KB per icon per push); `native.js` decoded with
`Uint8Array.from(bin, cb)`; and `loadApps(true)` re-pushed the whole list on every
tab-3 entry. Measured per tab switch: **decode 108.1 ms → 0.01 ms**, marshalled
1600 KB → 1200 KB, and an unchanged switch now pushes **nothing at all**.

**W7 — it was never a hang.** `SettingsPage` opened the password pane pinned to grid
column 1, but the Account pane is a full-span (minus rail) overlay — so the password
screen covered only the pane's DETAIL region. The Account hub beside it stayed visible
AND live: every row tapped opened its sublevel underneath the password pane, so nothing
moved and the surface read as frozen. Only `ixian:tab` cleared it because that is the
one path running `requestSettingsOverlayExit`, which disposes the whole SettingsPage.
This is #265 ② (Downloads), second instance. Fixed: the sublevel covers its opener
exactly (`column -1` + the opener's stage inset, so the rail stays live), plus a
SettingsPage close-audit. **Latent twin left in place:** `ixian:backup` still uses
`paneMode ? 1 : -1` — inert today because the shell renders Backup inline, same class
if that cap is ever dropped.

**W5 pattern, three fixes.** (a) Live-apply across WebViews using the `spixi.backup.last`
grammar (storage event + focus + visibility-guarded poll) — no reload, no new verb.
Found and fixed a bonus bug while there: a live `setTheme` left dark painting the LIGHT
intensity, because the ×0.36 derivation only ran at boot. (b) Light-mode faintness was
the **ink**, not the opacity ladder: `primary-200` is near-isoluminant with the sky
wash, so light Bold measured FAINTER than dark Subtle at 2.8× the opacity (1.03 vs
1.12). Moved light to `primary-400` → 1.08/1.14/1.20, parity with dark; dark renders
pixel-identical. (c) Live flow re-dialled — `speed 0.4→0.85 · spacing 20→15 · dash
4.5→7 · lineWidth 1→1.25 · fieldScale 95→44`. Root cause of "barely visible movement":
the dashes only ROTATE, so at 4.5 px a full second of drift moved an endpoint less than
a pixel — the field was animating correctly and rendering below the resolution of the
eye. `fieldScale 95` also made a 1100 px pane ~11 field units, so the whole field turned
as one slab. Motion 4.7× more perceptible; 0.42 ms/frame against a 40 ms budget.
**This supersedes Damir's 2026-08-12 locked dial.**

breaks money flows on a wide window. Full reasoning in DECISIONS #338. The trap:

FIRST — otherwise the rail ends up visible-but-inert, which is worse than covered.
