## Why the pre-warm was NOT pointed at these three pages

The prompt asked for an explicit answer with a recommendation, so: **rejected, and it is not
close.** #800's spare is priced at **~15 MB PSS each** (#803, four `dumpsys meminfo` readings
paired inside one process). Three spares is ~45 MB of resident memory to make a boot the app
still pays for happen *earlier*. The inline route removes the boot, costs nothing, and reuses
screens that have shipped on desktop since #243 / #267 / #341. The design question the fallback
would have forced — one shared spare, three, or a pool — does not arise.

## Found by the loop, NOT fixed — and why

★ **`HttpUtility.UrlDecode` form-decodes the wallet password.** A literal `+` becomes a space
before `writeWallet` and before `Preferences["walletpass"]`, on BOTH changepass hosts. It is
self-consistent in the app (unlock decodes the same way), so nobody has noticed — but
`ixian:backupWallet` shares a `wallet.ixi` whose real password is not the one the user typed,
and no other Ixian tool will open it. **INHERITED**, so by the handover gate's own rule it goes
to the BE engineer untouched, and it is now **security-review MAJOR #8** with the migration
shape written out. ⚠ **Do not "fix" it by tightening the decode**: users who already set a `+`
password have a wallet encrypted with the transformed string, and that change locks exactly
them out, permanently.

Also found, also left alone, each with its reason in
`docs/opus-review-verdict-session-q.md`: the decode that runs one statement before
`e.Cancel = true` in all 19 handlers (pre-existing, app-wide, unreachable today) · a HomePage
branch justified by `reloadAllPages`, which has no callers · the scrub that runs BEFORE the
220 ms exit slide, so the password fields visibly blank as the screen leaves (deliberate — a
scrub is not delayed for looks) · `settings.html` publishing no `--kb-inset`, which is
**parity** with the page it replaces, not a regression · `ixian:loadDownloads` being emitted
once per RENDER rather than once per open.

## ★ Damir, mid-session: "add apps and add contact stutters" — the same mechanism, and what it costs

Confirmed by reading the tree, not by analogy. **Add contact** and **Add app** are the only two
remaining rows on a hot route that push a C# page with its own WebView:
`HomePage.xaml.cs:826` → `ContactNewPage` (`contact_new.html`) and `:832` → `AppNewPage`
(`app_new.html`). Each pays the same cold Chromium boot #803 measured at 130–230 ms on the main
thread. That is why they feel like Backup and Password did.

**The cheap half is already taken.** Session K (#766) removed the 120 ms present-hold from both
(`revealDelayMs: 0` at both call sites, measured there at 126–185 → 252–332 ms on `AppNewPage`).
What is left is the WebView creation and parse, which only the #804 shape removes.

**It is NOT the three-token fix #804 was, and the difference is the whole estimate.** Those three
Account screens already existed inside `settings.html`, their caps were already pushed to the
phone and their verbs were already dispatched by `SettingsPage` — nothing had to move. These two
own their verbs on their own pages:

| page | verbs it handles |
|---|---|
| `ContactNewPage` | `ixian:onload` · `ixian:checkAddress:` · `ixian:viewcontact:` · `ixian:quickscan` · `ixian:back` |
| `AppNewPage` | `ixian:onload` · `ixian:fetch:` · `ixian:selectAppFile` · `ixian:error` · `ixian:back` |

Hosting them in `home.html` means migrating that dispatch to `HomePage` behind a new cap, with a
close-audit and the `formpane` routing preserved for desktop. The components exist already
(`createAddContact` / `setAddContactAddress` / `setAddContactKnown`, and `createAppsAdd` /
`setAddUrl` / `setAddError` are all bundle exports), and `home.html` already hosts the contacts
takeover through `mountContacts` — so the FE half is small. The C# half is not.

★ **`ixian:fetch:` is a security-gate row, not a routing change.** `AppNewPage` hands the URL to
`MiniAppManager.fetch(url)` and then `extractAppInfo` — a REMOTE fetch and a parse of what comes
back. Moving that dispatch onto `HomePage` puts it on the page that also hosts the chats list.
That is not the #221 chat wall, but it is a widening, and it needs the introduced-vs-inherited
lens before a line is written.

**Not built this session, on purpose.** The batch above is finished and reviewed; opening a
second surface would re-open the loop that just closed on a three-token change, and #294 says
measure first — there is no capture of these two surfaces at all. The walk gained rows **D1/D2**
so the F5 characterises them: if Backup/Password/Download come back smooth and these two still
stutter, that is the evidence that this fix is worth the C# it costs here.
